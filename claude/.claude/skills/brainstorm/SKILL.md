Make or revise the product brief, docs/BRIEF.md. Input: $ARGUMENTS

The `brief` skill (template, slots, writing rules, report line) is the planner's: name it in every planner call here and do not load it yourself. The brief is product level only — what is being built, for whom, what is in and out, how success is measured. Feature detail (a flow, a screen, an API) is welcome — the CEO will not be asked about it again: the planner keeps it verbatim in the brief's appendix and writes each spec section (docs/specs/) from it at /plan, when the feature's turn comes. Let the CEO say as much as they want; the brief's own Decided line stays one sentence.

0. If CLAUDE.md has no "## Language" section, first ask the CEO the working language with AskUserQuestion (options: ko / en / other; default: the language of the CEO's message, or of the file when the input is a file), run `node .claude/scripts/set-language.mjs --file CLAUDE.md <code>`, and continue in that language. Skip when it is already set.
1. Mode — from the injected board and the input (the only file read allowed here is a Grep of docs/BRIEF.md's `Status:` and `Kind:` lines):
   - board `Brief: … · brainstorm (checkpoint k)` → have team-planner report the whiteboard (decided / later / rejected / open) and continue the brainstorm from there (step 2).
   - board `Brief: … · draft` → have team-planner report the brief line (open slots, defaults, the critic's findings if recorded) and continue at step 4; `correction k` → step 5.
   - board `Brief: … · revision (checkpoint k) | revision draft | revision correction k` → revision mode (below) resumes at the matching step: checkpoint → step 2, draft → step 4, correction → step 5.
   - docs/BRIEF.md with `Status: approved` or `revised` (and no revision on the board) → revision mode: say so in one sentence and ask what changed; the whiteboard is kept on top of the existing brief (step 2) under "## Whiteboard (revision)", the Status line keeps its date and gains ` (rev n draft)` (the original approval is rev 1), the board's Brief line reads `revision …` instead of `brainstorm …`, and the compile writes only the differences.
   - the input names an existing file, or is pasted text longer than a few lines → entrance B: hand it to team-planner (the path, never the contents; pasted text verbatim) to normalize into docs/BRIEF.md per the template, keeping the CEO's wording, `Source:` = the path; the original stays untouched and is linked, never pasted. Tell the CEO they can keep talking (step 2) or go straight to step 3.
   - otherwise (an idea, or nothing) → entrance A, step 2.
2. Brainstorm — brainstorm mode (team-lead principles): no agenda and no slot list. The CEO throws ideas; you propose, push back, sketch alternatives and name costs, at length when useful. Keep a whiteboard in your head: decided / later / rejected with the reason / open. Every ten or so exchanges — and always before a /handoff or when compaction looms — checkpoint it: one team-planner call with the CEO's messages verbatim and each of your proposals the CEO accepted, quoted, in order; the planner appends them to docs/BRIEF.md under "## Whiteboard" (`Status: whiteboard` in create mode; in revision mode the existing Status line stays and carries `(rev n draft)`) and reports the brief line; update the board yourself (the `resume` skill's Board format, loaded once at the first board write; on docs/STATUS-team.md `Brief: docs/BRIEF.md · brainstorm (checkpoint k)`, or `revision (checkpoint k)` in revision mode; next action `/brainstorm`). The brainstorm ends when the CEO asks for the document ("기획서 만들어줘", "정리해줘", "write it up", or the like); a CEO who opens with a full description and asks for the document at once skips straight to step 3.
3. Compile and pre-mortem — one turn, the CEO not in between. (a) One team-planner call with every fragment since the last checkpoint verbatim. Create mode: the planner rewrites docs/BRIEF.md per the template, sorting ideas into decided / later / rejected (with the reason), keeping feature sketches in the appendix verbatim, grouped by feature, and moving a requirement list with IDs into docs/BACKLOG.md (`req:` items; the brief keeps a pointer); every slot the brainstorm did not settle gets the planner's default with its reason (`default: <x> — <reason>`), except the non-goals, which stay Open — they are the CEO's word. Revision mode: only the differences, a Revision-history line, the charter lines the change touches, the whiteboard section removed and the Status line still `approved|revised <date> (rev n draft)`. Either way the planner reports the brief line — the Open slots and the defaults it set. (b) In the same turn, have team-critic review docs/BRIEF.md (target `brief`, the planner's brief line as the facts block; revision mode: also docs/CHARTER.md and the board's Plan line). Skip the critic only when the CEO says so. Update the board (`draft`, or `revision draft`).
4. The one round — one numbered message in plain chat, three parts: the Open slots (normally the three concrete non-goals, plus an item the planner flagged); the defaults the CEO should see — the success metric always, the milestone and kill criterion, the constraints and the deadline — each as `default: <x>; say so to change it`; and the critic's findings, one line each with the planner's default. Answers may arrive in several messages (acknowledge in one line, close on "여기까지" / "됐다" / a question back, or when every Open slot is answered); an item the CEO does not mention keeps its default. Then one planner call with the fragments verbatim; board `correction 1` (revision: `revision correction 1`). "Your call" on an item that costs money or touches security becomes `undecided — planner default: <x>; confirm at the /kickoff ADR question` (or `at the /assess strategy question`); what is still disputed goes under Undecided.
5. Approval — one AskUserQuestion: approve / correct (the CEO says what is wrong in plain chat, the planner revises — one more round, the second and last; board `correction 2` — then ask again) / stop here (stays draft; nothing is committed; the board keeps its state). Approval is the go: nothing else is asked before /kickoff or /assess, and the CEO does not say "진행해". On approve:
   - team-planner sets `Status: approved <date>` and `Corrections: <k>` — in revision mode `revised <date> (rev n)`, applying the charter edits it listed and keeping docs/CHARTER.md under 60 lines;
   - write the board (STATUS-team Now: `Brief: docs/BRIEF.md · approved · Kind: <kind>`; after a revision `Brief: docs/BRIEF.md · revised (rev n)` while the existing Plan line stays — /backlog clears it; Next actions: 1. `/kickoff` for Kind 신규, `/assess <path>` for Kind 레거시, `/backlog` after a revision);
   - commit by path yourself — docs/BRIEF.md, docs/BACKLOG.md when seeded, docs/CHARTER.md when revised, docs/README.md, CLAUDE.md (its Language section), docs/STATUS.md, docs/STATUS-team.md, .gitignore if untracked, and .claude/ if not yet tracked — as `docs(brief): <title> — approved` on main (branches-and-sync rule; if the checkout is on another branch, ask the CEO first) or, for a revision, `docs(brief): revised — <summary>` on the current branch — then continue with that command (`kickoff` or `assess`) in the same turn, unless the brainstorm was long (a compaction happened): then say in one sentence to start a new session and say 계속 — the board's next action carries it.
