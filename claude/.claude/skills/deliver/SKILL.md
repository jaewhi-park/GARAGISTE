The lead starts it when the CEO says go ("진행해", "계속", "시작해") or when a session opens with `Mode: running`; it stops at the cap, when every remaining item waits on a hard stop, at a third compaction, an empty backlog or "멈춰" — a new screen, a first run or a default decision is a checkpoint on the CEO's page, never a stop

Run the team until it must stop. Note: $ARGUMENTS

The board's `Mode:` line is the contract with the CEO: `running` from the first step here to the pause at the end, `waiting on CEO` while a hard stop is open and nothing independent is left, `paused — …` when the team is looking at the CEO and doing nothing else. Every step is re-entrant (the `resume` skill's Continuity section): a session that opens with `Mode: running` re-enters here after `resume` and continues with the plan and step the board names — the CEO never has to repeat the go. Nobody may be watching (a scheduled or scripted session, the CEO away): the headless rule at the end holds in every session.

0. Iteration plan. Apply the branches-and-sync rule (on main, synced). An iteration is the run between two CEO reviews; it ends at the unattended cap — the operating profile's `unattended cap` (default `8 plans | 2 sections`: 8 plans shipped, or 2 spec sections whose Status turned `done`, whichever comes first; the note may name a smaller cap or the items). From docs/BACKLOG.md — a `rework:` or `bug:` item first, then the priority order (the order the CEO fixed, if any) — take the items in order. A Plans line already on the board is the pick — the kickoff's iteration 1 (the walking skeleton alone, so the CEO sees it before anything is built on it) or a `Next iteration` line left by the last review. Write the board's Iteration block (`Plans: <item ✓ | ▶ step k/n | —>… · cap: <n> plans | <m> sections`), set `Mode: running`, commit the board (`docs(status): iteration <k> start`) and tell the CEO the goal in one line. Do not wait for an answer.
1. For each item, in order:
   a. `cat .claude/session/compactions` — at 3 or more, the compaction cut (the `resume` skill's Continuity section) applies before a new plan starts.
   b. Run `plan` via the Skill tool (the item) — unless the item is already an approved plan path (docs/plans/0001-… after a kickoff or an assess): then skip to c. The critic's APPROVE is the approval.
   c. Run `run` via the Skill tool (the plan path): build → review → ship. /ship merges when the lead may (lead-merge: risk:low, verifier PASS, every lens APPROVE, required checks green when there is a remote); a `risk:high` plan is merged by the lead as well while the board's Stage is `pre-launch`; at `live` it is the CEO's word, asked by /ship from the PR's Risk summary — a hard stop, handled as in e.
   d. Board: mark the item ✓ on the Iteration line, fold what can now be tried into the CEO page's Try it script (one script for the iteration — the "Try it" steps of the PR when it has them, in plain words), and write the checkpoints of step 2.
   e. A hard stop — one of the lead's four escalation items, or a live `risk:high` merge — never stops the team: park that plan (its question with the default on the CEO page's For you, the plan on its branch, the board's Plan line `parked — <question>`) and take the next backlog item whose files and depends-on are independent of it; the run continues. Only when nothing independent is left: `Mode: waiting on CEO`, end the turn. The CEO's next message resumes here; "기본값대로" takes every parked default.
2. Checkpoints — a line on the CEO's page, never a stop: a new screen or a first successful run (the plan's `shows:` lines; the board's Run line changing from `not yet`) → one For you line saying what to open and what to look at; a spec section turned `done` (the ship step's Status update) → one For you line naming the section's core flow; a decision taken by default → Decided by default (at most five lines; the oldest drop as the review closes). The CEO reads them at the cap; a checkpoint that could not wait is a hard stop only when it meets the four items.
3. Iteration end — at the cap, an empty backlog, or every remaining item parked: run the retro trigger (below), set `Mode: paused — iteration review`, rewrite the CEO's page for the review (Try it = this iteration's one script; For you = at most three lines, the ones still open; Decided by default = this iteration's), write the `Next iteration` line (the items it would take, from the backlog), commit the board (`docs(status): iteration <k> review`), and send the iteration review — this form, nothing else, labels included in the team's language ("## Language" in CLAUDE.md), then end the turn and do nothing until the CEO speaks:
   - Try it: `<run command>` → <the 3–5 steps, from the CEO's page>
   - Changed this iteration: <plans, one line each>
   - For you: <the page's lines> | none
   - Decided by default: <the page's lines> | none
   - Retro: <up to three numbered proposals from the trigger, each `applied` (a rule line, already in) or `proposed`> | none
   - Next iteration: <the items it would take>
   - Tried? answer in one line — `써봤다 · <what worked, what did not>` or `안 써봤다` — then 계속 (this session or a new one; the board carries everything).
   The answer goes on the board (STATUS-team `Tried (last review):`); the next ship copies it into the `acceptance` column of this iteration's docs/METRICS.md lines (`tried: ok | tried: <issue> | not tried`). Two reviews in a row `not tried` → say so in one line before the next plan starts, and continue. "계속" starts the next iteration; "1, 3 반영하고 계속" applies those retro proposals first; anything else is an instruction (the `instruction` skill) or a question.
   Retro trigger: read this iteration's docs/METRICS.md lines and the board's Counts; when any plan shows `rev 3` or higher, a fix loop past its cap, verifier FAIL 2 or more, a review round 1 with more than 10 majors, a `bug:` or `rework:` item naming a shipped slug, a `tried: <issue>` acceptance, or a CEO question outside the four escalation items, run `retro` via the Skill tool in its mini mode (subject: those plans) and carry its numbered proposals into the review; otherwise `none`. A proposal that is one rule line (CLAUDE.md, a memory file, a "## Risk paths" or "## UI paths" glob) is cheap to reverse: `retro` applies it and it goes under Decided by default — the CEO overturns it by number; a proposal that changes a skill, an agent or a hook waits for the CEO's number.
4. Other stops — in each case the board says what is committed and what comes next, and the turn ends:
   - every remaining item parked on a hard stop: `Mode: waiting on CEO`, the defaults on the board;
   - a merge conflict you may not resolve: `Mode: paused — blocked: <what>`, the report in the final-report format (a fix loop past its cap is not a stop — the loop rule cuts the plan and the run continues);
   - a third compaction (the count is 3 or more): finish the step in progress, commit the board with `Mode: running` kept, and tell the CEO to start a new session and say 계속;
   - "멈춰" / "stop": finish the step in progress, commit the board, `Mode: paused — stopped by CEO`.

Headless rule — nobody may be watching, so a question mid-run is never asked: take the default the skill names, put it under Decided by default (docs/DECISIONS.md when hard to reverse) and continue; a hard stop is parked as in 1e. AskUserQuestion is for the iteration review, /brainstorm, /kickoff and a hard stop with nothing independent left — and even then the board carries the question with its default, so the turn ends cleanly without an answer and the next message, whenever it comes, resumes here.
