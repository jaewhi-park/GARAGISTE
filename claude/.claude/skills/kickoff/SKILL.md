Start a new project from the approved product brief. Note: $ARGUMENTS

The brief's approval was the CEO's "go": from here the team decides and logs; the CEO answers one question (the stack — the most expensive decision to reverse — and the budget) and anything on the escalation list, nothing else. This command writes documents only — no code, no verifier: the scaffold is the first step of plan 0001 and goes through the normal build → review → ship loop in iteration 1. Every step is re-entrant: an output that already exists (the file, the commit) is skipped.

0. Precondition: docs/BRIEF.md with `Status: approved` or `revised` and `Kind: 신규` (from the injected board's Brief line, else Grep those two lines — the one file read allowed here). If there is none, or it is still whiteboard or draft, say so in one sentence — "run `/brainstorm <idea, or the path of a document you wrote>` first" — and stop; with `Kind: 레거시`, say so and suggest `/assess <path>` instead. If CLAUDE.md has no "## Language" section (a brief committed from elsewhere), ask the CEO the working language with AskUserQuestion (options: ko / en / other; default: the language of the brief), run `node .claude/scripts/set-language.mjs --file CLAUDE.md <code>`, and continue in that language.
1. One team-planner call (name the `charter`, `design` and `security` skills — it reads them): (a) derive docs/CHARTER.md from docs/BRIEF.md per the `charter` skill (under 60 lines, `Source: docs/BRIEF.md`; a slot the brief leaves undecided gets the planner's default with the reason and a docs/DECISIONS.md line — never a guess presented as fact); (b) write docs/adr/0001-stack.md with 2–3 stack/architecture alternatives and a recommendation, `Status: proposed`, its Context taken from the brief's constraints and risks, plus two sections the recommendation carries as decisions, one line each: "Design foundation" per the `design` skill (component library or primitives, tokens, layout shell, the screenshots command — when the brief has a UI) and "Security baseline" per the `security` skill (every line decided or "not applicable — <why>"). No critic here: it reviews the ADR in step 3 together with the spec and the plan. Then the one AskUserQuestion call of this command: the stack (the planner's recommendation first, with its reason), the budget tier (unlimited = API/in-house / high = Max 20x / medium = Max 5x / low = Pro), and any brief Undecided item that meets the escalation criteria (paid services, security or user data, a non-goal conflict) with the planner's default — every other Undecided item is the planner's default, logged. The answers go to the planner verbatim in step 2 and to `hire` in step 4.
2. Two team-planner calls in one turn, in parallel, each with the step-1 answers verbatim:
   - Rules and decisions (name the `claude-md` skill): (a) write CLAUDE.md per the `claude-md` skill — "## Commands" holds the chosen stack's standard commands (setup, quick and full verification, the run-one-test-file form, build/run, `screenshots:` when the stack has a UI, the audit command in full verification), each ending in ` — unverified` until team-verifier has run it (the /assess convention: the full verification at the end of plan 0001's build removes the marker); "## UI paths" seeded from the design foundation (screens, components, styles) and "## Risk paths" from the security baseline — the migration, schema, auth, public-API, dependency-manifest and CI/deploy paths this stack has; (b) set docs/adr/0001-stack.md to `Status: accepted` with the CEO's choice and record the step-1 answers and every default in docs/DECISIONS.md (and the brief's Undecided list).
   - Spec, backlog and the first plan (name the `spec` skill): (c) write the core spec per the `spec` skill — a docs/specs/F<nn>-<slug>.md only for the Decided lines the brief's core flow (its demo scene) touches, and the docs/SPEC.md index with a row for every Decided line: the rows without a file yet are `Status: pending`, File `—`, and /plan writes the file when the item's turn comes (the spec skill's Extending rule); the appendix sketches verbatim in their sections, defaults for the rest — and report the spec report line; (d) write docs/BACKLOG.md — one item per index row (`spec: F<n>`; completion criteria = the section's Done-when when the file exists, else the brief's Decided line, marked `pending section`), Later lines as P2, Non-goals under "Excluded"; when /brainstorm already seeded docs/BACKLOG.md from a requirement list, keep those items and add only what is missing — and docs/plans/0001-walking-skeleton.md: step 1 is the scaffold (kind: scaffold — the stack per the ADR, the design foundation's shell and tokens when the brief has a UI, the security baseline's standard protections, the test runner wired into the quick verification and one smoke test that asserts something about the skeleton; its verification command is the rules file's quick verification), the remaining steps the thinnest end-to-end slice of the brief's core flow through the F-sections it touches, no styling; section 5 says the plan is slower for the harness step.
3. Have team-critic review, in one call, target `kickoff`: the stack ADR, the spec (every docs/specs/ file and the index) and the walking-skeleton plan (the first plan is always reviewed) — with the facts block of the `plan` skill's critic call (here: no test harness yet, plan 0001's step 1 is it; the index rows; the planner's spec report line; the charter's Non-goals and Constraints pasted). Findings go to the planner verbatim, one round: what it still marks `stands` is attached to the report; a finding only the CEO can settle — an escalation item — goes to the CEO at once with AskUserQuestion, default attached. The critic's APPROVE on the plan is its approval; with a blocker still open after the round, one AskUserQuestion call — approve as is / stop here.
4. Commit the files this command wrote yourself, by path — docs/CHARTER.md, docs/adr/0001-stack.md, docs/SPEC.md, docs/specs/, docs/BACKLOG.md, docs/plans/0001-walking-skeleton.md, docs/DECISIONS.md, docs/BRIEF.md if changed, CLAUDE.md, docs/README.md, docs/STATUS.md, .gitignore if untracked, and .claude/ if not yet tracked — on main, as `docs(kickoff): charter, stack ADR, spec, backlog, plan 0001`. Then run `hire` via the Skill tool with the budget tier from step 1 and the project's character from the brief (it applies without a second question and shows the roster; the CEO changes a line by saying so). Write docs/STATUS.md (`Mode: running` · Stage: pre-launch · Run: not yet (the CLAUDE.md build/run line once plan 0001 ships) · Iteration 1 · Plans: docs/plans/0001-walking-skeleton.md — · Now: none · Next actions: 1. `deliver` — iteration 1, in a new session) and commit it by path (`docs(status): kickoff done`). End with one report — the spec sections (F1–F<n>, one line each, the pending ones marked), what was decided by default (a pointer to docs/DECISIONS.md), the roster — and one sentence: start a new session and say 계속 (model assignments load at session start; the board's Mode makes that session continue by itself). Do not start the iteration in this session.
