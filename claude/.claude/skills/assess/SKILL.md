Assess an existing codebase and set a rebuild/modernization strategy. Target and context: $ARGUMENTS (when no path is given, the brief's Kind line names it)

0. Precondition: docs/BRIEF.md with `Status: approved` or `revised` and `Kind: 레거시 (<path>)` (from the injected board's Brief line, else Grep those two lines — the one file read allowed here) — the brief holds why the rebuild happens, the target state, what must not change and the deadline. If there is none, or it is still whiteboard or draft, say so in one sentence — "run `/brainstorm <why, target state, what must not change, deadline>` or `/brainstorm <path of a document you wrote>` first" — and stop; with `Kind: 신규`, say so and suggest `/kickoff` instead. If CLAUDE.md has no "## Language" section (a brief committed from elsewhere), ask the CEO the working language with AskUserQuestion (options: ko / en / other; default: the language of the brief), run `node .claude/scripts/set-language.mjs --file CLAUDE.md --settings .claude/settings.json <code>`, and continue in that language.
1. Load the `legacy-assessment` skill. Send the Explore subagent out per area in parallel to gather the inventory, and have team-planner (name the `claude-md` skill) compile docs/ASSESSMENT.md — pass the Explore reports to it verbatim, do not re-summarize, and name docs/BRIEF.md so it marks every "looks like a bug" item that conflicts with the brief's target state or invariants — and, in the same call, write CLAUDE.md per the `claude-md` skill: "## Commands" = the build/test commands the inventory found, each ending in ` — unverified`; "## Risk paths" seeded from the risk register. Then have team-verifier run the Commands section (one call; the results go to the planner in step 3, where the marker comes off).
2. Report unknowns in chat, then get the preserve/fix policy in one AskUserQuestion call (split only if the tool limits questions per call): the question names each "looks like a bug" item with the planner's default (preserve, per the `parity-harness` skill) and offers "accept all defaults" first and "decide per item" second (then one question per item in follow-up calls); items the planner marked as conflicting with the brief get their own question. The answers go to team-planner verbatim in step 3 and are logged in docs/DECISIONS.md there.
3. Have team-planner compare strategies (strangler fig / module-by-module replacement / full rewrite) with a recommendation and the first seam to replace, written directly as docs/adr/0001-rebuild-strategy.md with `Status: proposed`, and in the same call derive docs/CHARTER.md from docs/BRIEF.md and the assessment (name the `charter` skill; under 60 lines, `Source: docs/BRIEF.md`: Problem, Users and Constraints from the brief; Success metrics = parity PASS for every rebuilt seam plus the brief's success metric; Non-goals = the brief's non-goals, the rejected strategies and the seams out of scope; the preserve/fix decisions under Constraints; other sections `undecided — at the first /retro`). No critic here: it reviews the ADR in step 4 together with the rebuild plan and plan 0001. Then the one AskUserQuestion call of this command: the strategy (the planner's recommendation first, with its reason), the budget tier (unlimited = API/in-house / high = Max 20x / medium = Max 5x / low = Pro), and any brief Undecided item that meets the escalation criteria (paid services, security or user data, a non-goal conflict) with the planner's default — the charter lines and every other Undecided item are the planner's defaults, logged. Then one team-planner call (name the `parity-harness` skill; pass the answers and the verifier's per-command results verbatim): sets the ADR to `Status: accepted` with the CEO's choice, records the answers and every default in docs/BRIEF.md and docs/DECISIONS.md, removes the ` — unverified` marker from the CLAUDE.md commands that passed and drops what failed (a command the guardrail blocked stays marked — tell the CEO its tool must be added to the verifier allow-list by a human), seeds "## Risk paths" with the chosen seams, writes docs/REBUILD_PLAN.md (step 0 of every rebuild step: extend the parity harness to that step's seam) and docs/plans/0001-parity-harness-<seam>.md — the harness for the first seam per the `parity-harness` skill, whose last step registers the runner under Commands (do not invoke `/plan`).
4. Have team-critic review, in one call, target `assess`: the rebuild ADR, docs/REBUILD_PLAN.md and the parity-harness plan (legacy work is always reviewed) — with the facts block of the `plan` skill's critic call (here: the verifier's per-command results; the preserve/fix decisions; the charter's Non-goals and Constraints pasted). Findings go to the planner verbatim, one round: what it still marks `stands` is attached to the report; a finding only the CEO can settle goes to the CEO at once with AskUserQuestion, default attached. The critic's APPROVE on the plan is its approval; with a blocker still open after the round, the `plan` skill's cap rule: it becomes the plan's first step or splits the plan — no question.
5. Commit the files this command wrote yourself, by path — docs/ASSESSMENT.md, docs/CHARTER.md, docs/adr/0001-rebuild-strategy.md, docs/REBUILD_PLAN.md, docs/plans/0001-parity-harness-<seam>.md, docs/DECISIONS.md, docs/BRIEF.md if changed, CLAUDE.md, docs/README.md, docs/STATUS.md, docs/STATUS-team.md, .gitignore if untracked, and .claude/ if not yet tracked — on main (if the legacy checkout is on another branch, ask the CEO first), as `docs(assess): assessment, charter, rebuild ADR, rebuild plan, plan 0001`; the legacy tree's other uncommitted changes stay untouched. Run `hire` via the Skill tool with the budget tier from step 3 and the project's character from the brief (it applies without a second question and shows the roster) — a rebuild weights critic and reviewer heavily, so assign in that direction; the brief says how much rides on it. Write the board (docs/STATUS.md: `Mode: running` · Stage: live · Run: the CLAUDE.md build/run line · Try it, For you, Decided by default: none; docs/STATUS-team.md: Iteration 1 · Plans: docs/plans/0001-parity-harness-<seam>.md — · Now: none · Next actions: 1. `deliver` — iteration 1, in a new session) and commit it by path (`docs(status): assess done`). End with one sentence: start a new session and say 계속 (model assignments load at session start; the board's Mode makes that session continue by itself). No rebuild step starts before that plan ships with the harness PASS against legacy.
