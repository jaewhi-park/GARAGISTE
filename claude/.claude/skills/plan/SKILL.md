description: Plan a piece of work — intake (one question call, optional spec rounds) → planner writes → critic reviews → CEO approval requested; `<spec or plan file> 수정: <what changed>` revises an approved spec or amends a plan (a running plan continues on its branch)
argument-hint: "[backlog item, bug: line, feature, docs/specs file, or <spec|plan file> 수정: what changed]"

Plan the following work: $ARGUMENTS

If the argument names a docs/plans/ file (with or without `수정:`), or a docs/specs/ file followed by `수정:` (or `revise:`) and what changed, take the revision path (step 0b) and skip the intake and the branches-and-sync rule — a running plan is amended on its own branch. Otherwise, before the intake apply the branches-and-sync rule (on main, synced; in a linked worktree stay on its branch) — the approval commit lands there.
0. Intake — one AskUserQuestion call before delegating anything. Skip it when the request already carries a verifiable done-when:
   - it quotes a docs/BACKLOG.md item by title or number (take the CEO's word that it exists; Grep only that item's lines for its size and `spec:` field — the one file read allowed here; the planner pulls its completion criteria). An item without a `spec:` link that is size L or names a new page, screen, API or data model still gets question (1) alone; an item with a `spec:` link draws nothing.
   - it describes a defect with a reproduction rather than new behaviour (`bug:` / `버그:`)
   - it names a docs/REBUILD_PLAN.md step (done-when is parity-harness PASS) or references a docs/specs/ file (a docs/plans/ file, or a docs/specs/ file with `수정:`, is the revision path, step 0b, not an intake case)
   - it states done-when and not-this-time itself, in the argument or earlier this session
   Four questions; (1) has exactly its two options, (2)–(4) have two options drawn from the request and the auto-injected charter, recommendation first, plus "your call" (recorded as unverified with the planner's default) and "decide in the spec rounds" — four per question, the tool's limit; the CEO can always type their own answer. Do not call Explore for the intake.
   (1) detailed spec? — no, plan from these answers (for a BACKLOG item: from its completion criteria; recommended for S/M) / yes, build docs/specs/NNNN-<slug>.md first (recommended for a new page, screen, API or data model, or more than a day of work)
   (2) done when — verifiable completion criteria
   (3) not this time — adjacent work left out
   (4) fixed in advance — "nothing beyond the charter", or things to reuse or match (existing screen or component, library, design, deadline)
   If (1) is no and (2) is "decide in the spec rounds", (1) becomes yes — say so in one sentence; done-when cannot be defaulted. The same answer on (3) or (4) with (1) no counts as "your call".
0a. Spec — if (1) is yes, load the `spec` skill and follow its rounds (the answers to 2–4, or the BACKLOG item's completion criteria when only (1) was asked, seed the spec). On "approve, plan now" continue; on "approve, plan next session" or "stop here" have team-implementer commit the spec and, for a BACKLOG item, docs/BACKLOG.md (`docs(spec): NNNN-<slug> approved|draft`, by path), write docs/STATUS.md (Spec line; Next actions: 1. `/plan docs/specs/NNNN-<slug>.md` in a new session) and end by suggesting that in a sentence — no /handoff needed. A docs/specs/ file passed as the argument re-enters here — load the `spec` skill and take the spec's state from the injected STATUS.md Spec line (else have team-planner report it): approved or in progress → no questions, go to step 1; round k or correction k (rounds interrupted, also after a compaction) → have team-planner report the open slots and continue from that round; draft (stopped after the rounds) → the approval question only.
0b. Revision — the five moves of /brainstorm's revision mode, for an approved spec (`Status: approved` or `in progress`) or a plan (approved, or running on plan/<slug> — stay on that branch, never switch). (1) Brainstorm mode: discuss the change — the options, what it touches, its cost; for a plan, the board's Step line and `git log --format=%s main..HEAD` tell you which steps are already committed. (2) When the CEO says "정리해줘" / "write it up": one team-planner call with the discussion verbatim (for a spec, load the `spec` skill first — its Revision section). A spec: only the differences (Done-when, Not-this-time, Undecided), `Status: … (rev n draft)`, a Revision-history line, the BACKLOG item's completion criteria when it has one, and an impact report — plans in flight (the board's Plan line and step), shipped plans (docs/METRICS.md lines naming the spec), conflicts with docs/CHARTER.md or the brief's non-goals. A plan: only the steps after the last PASS the board records (all steps when none ran), header `Revised: <date> (from step k, draft)`, sections 1–2 changed only when the source spec or brief changed (the Source line names the spec's rev), the step-size rules as usual. Update the board (`Spec: … rev n draft` or `Plan: … rev n draft`). (3) team-critic reviews only the changed parts — a spec: does it invalidate shipped work, can the plan in flight absorb it in its remaining steps, does it widen past the brief's non-goals or the charter; a plan: are only steps after the last PASS changed, does each changed step keep a verification command and the size rules, is it consistent with the spec's current rev. Findings only the CEO can settle go to the CEO in plain chat as the correction round (a spec: usually all of them); the rest to the planner per the critic loop. (4) One AskUserQuestion: approve / correct (the CEO reads the file and corrects in plain chat; the planner revises; ask again — max 2) / stop here (nothing committed; the file keeps its draft rev). (5) On approve: the planner sets `Status: approved <date> (rev n)` (a spec in progress keeps `in progress` with the rev noted; a plan loses the `, draft` marker in its Revised header) and, when shipped plans are affected, records one BACKLOG item `spec NNNN rev n — <delta>` (recording only); team-implementer commits by path — a spec: `docs(spec): NNNN-<slug> rev n` on the current branch; a plan: `docs(plan): NNNN-<slug> rev n` on its plan/<slug> branch, or on main when it has no branch yet. Update the board (the rev on the Plan or Spec line; Step unchanged) and end with one sentence — a spec with a plan in flight: "run `/plan <plan path> 수정: spec rev n 반영`"; a plan: "run `/run <plan path>` — it continues at step k+1 on the same branch". Never start /run yourself.
1. Have team-planner write docs/plans/NNNN-<slug>.md. Pass the request text and the intake answers verbatim under a "CEO requirements" heading, or the spec path (also the `spec:` path of a BACKLOG item that has one): they become the plan's Source line (with the BACKLOG item's `req:` ID when it has one) and sections 1–2 as given, and anything the planner adds beyond them is marked unverified with a default; for a spec-backed plan the planner also sets the spec's Status to `in progress — plans: <plan path>` (appending when plans are already listed). If the work would need more logic steps than the plan-size target (the operating profile; default 4) and BACKLOG does not already hold its parts, the planner first proposes a split — parts cut by tryable outcome (each ends in something that runs and can be tried), never by layer — 2–3 plans, each "part k of n of <spec or item>": goal / done-when subset / expected files / depends-on / size; ask the CEO which part to plan first and have the other parts recorded as BACKLOG items — recording only (title, value, completion criteria from the spec or the request, size, dependencies, `spec:` link when there is one; priority "undecided — next /backlog"), no prioritizing — noted as /parallel candidates only if expected files are disjoint and depends-on is empty. When the work is already split, the planner plans the part named in the request, else the next part whose depends-on are shipped. Make the plan reference the charter, CLAUDE.md, BACKLOG and ASSESSMENT/REBUILD_PLAN when they exist.
2. If the plan's `Risk:` header says high, its `Steps:` line is over the plan-size target (the operating profile; default 4), or it is the first part of a split (the critic reviews the cut once; later parts skip it), have team-critic review it — pass the plan path and, when one exists, the spec path (from the argument, the BACKLOG item's `spec:` field or the planner's report); otherwise skip. On REVISE, pass the findings verbatim to the planner (max 2 rounds, per the critic loop).
3. If any item meets the escalation criteria and neither the intake answers nor the approved spec already decided it, ask the CEO with AskUserQuestion; decided items go in plan section 6 as "decided — per intake/spec", not re-asked. If a step needs a capability no role has (a permission boundary or a separate judge), say so and suggest `/recruit <gap>` in a sentence.
4. Request approval with a summary (goal, step count, risks, expected diff, section 6 one line each) — one AskUserQuestion: approve / correct (the CEO reads the plan and corrects in plain chat; the planner revises; ask again — max 2) / stop here (nothing committed). Once approved: have team-implementer commit the plan together with any spec, BACKLOG or DECISIONS change this command made (`docs(plan): NNNN-<slug>`, by path) — the plan file does not change during /run except through the `수정:` path, so this commit is final and worktrees can see it; write docs/STATUS.md (Plan: <path> · Branch: none yet · Shipped: — · Next actions: 1. `/run <path>`); then do not call it via the Skill tool — suggest to the CEO in a sentence: "run `/run <path>`" (same session; a new session only after long spec rounds). Never start /build or /run yourself.
