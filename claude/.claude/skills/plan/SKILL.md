---
name: plan
description: Plan a piece of work — the planner writes from the spec section (or the bug line, the rebuild step, the request), the critic reviews every plan and its APPROVE is the approval; `F<n> 수정: <what changed>` revises a spec section, `<plan file> 수정: <what changed>` amends a plan (a running plan continues on its branch)
argument-hint: "[backlog item, F<n>, bug: line, feature in your words, or <F<n>|plan file> 수정: what changed]"
---
Plan the following work: $ARGUMENTS

No questions are asked before planning: the source of a plan is a document or the request itself, and the planner decides open slots with defaults it logs (docs/DECISIONS.md). The CEO is asked only through the escalation list (step 3). If the argument names a docs/plans/ file (with or without `수정:`), or a spec section `F<n>` followed by `수정:` (or `revise:`) and what changed, take the revision path (step 0b) and skip the branches-and-sync rule — a running plan is amended on its own branch. Otherwise apply the branches-and-sync rule first (on main, synced; in a linked worktree stay on its branch) — the approval commit lands there.

0. Source — resolve without asking, in this order:
   - a spec section (`F3` — docs/specs/F03-<slug>.md via the docs/SPEC.md index; or a BACKLOG item whose `spec:` field names one): the section's Done-when and Not-this-time are the plan's sections 1–2 verbatim; when the section's Done-when is more than the plan-size target can cover, the planner splits by tryable outcome (below).
   - a defect with a reproduction (`bug:` / `버그:`): the reproduction is the specification — a failing reproduction test first, then the fix; no spec section.
   - a docs/REBUILD_PLAN.md step: done-when is parity-harness PASS (docs/PARITY.md is the spec).
   - a BACKLOG item without a section, or a feature described in the CEO's words: one team-planner call first adds a section file under docs/specs/ (and its index row) per the `spec` skill's Extending rule (the CEO's words verbatim, defaults for the rest, logged), reported with the spec report line; then the plan is written from it. A request that would cross a brief non-goal or a charter constraint stops here: say so in one sentence and suggest `/brainstorm` (a brief revision) instead of planning around it.
0b. Revision — for a spec section (`F<n> 수정:`) or a plan (approved, or running on plan/<slug> — stay on that branch, never switch). (1) Brainstorm mode: discuss the change — the options, what it touches, its cost; for a plan, the board's Step line and `git log --format=%s main..HEAD` tell you which steps are already committed. (2) When the CEO says "정리해줘" / "write it up" — or at once when the change is one sentence and unambiguous — one team-planner call with the discussion verbatim (for a section, load the `spec` skill first — its Revision section). A section: only the differences, `rev n`, a Revision-history line, the BACKLOG item's completion criteria when it has one, and the impact report (plans in flight, shipped plans from docs/METRICS.md, charter or brief conflicts). A plan: only the steps after the last PASS the board records (all steps when none ran), header `Revised: <date> (from step k)`, sections 1–2 changed only when the source section or brief changed, the step-size rules as usual. (3) Sort the plans from the impact report: shipped work the change invalidates → one BACKLOG rework item per plan (`rework: <slug> — <delta>`); the plan in flight → amended in the same call or the next; unstarted plans → re-planned when their turn comes. (4) team-critic reviews only the changed parts — a section: does it invalidate shipped work, can the plan in flight absorb it in its remaining steps, does it widen past the brief's non-goals or the charter; a plan: are only steps after the last PASS changed, does each changed step keep a verification command and the size rules, is it consistent with the section's current rev — max 2 rounds per the critic loop. (5) The CEO is asked (one AskUserQuestion call) only when shipped work is discarded — name the plans and what is lost, default: proceed; every other revision proceeds on the critic's APPROVE. (6) Update the board (the rev on the Plan or Spec line; Step unchanged) and commit by path together with the file — a section: `docs(spec): F<n> rev n` on the current branch; a plan: `docs(plan): NNNN-<slug> rev n` on its plan/<slug> branch, or on main when it has no branch yet. Then continue: a section with a plan in flight → amend that plan (`plan <plan path> 수정: F<n> rev n 반영`) in the same turn; a plan → `run <plan path>` continues at step k+1 on the same branch when `Mode: running`, otherwise say so in one sentence and wait for the go.
1. Have team-planner write docs/plans/NNNN-<slug>.md. Pass the source verbatim — the section ID (also the `spec:` field of a BACKLOG item), the bug line, the rebuild step, or the request text under a "CEO requirements" heading: it becomes the plan's Source line (with the BACKLOG item's `req:` ID when it has one) and sections 1–2 as given; anything the planner adds beyond them is marked unverified with a default. For a section-backed plan the planner also sets the section's Status to `in progress — plans: <plan path>` (appending when plans are already listed). If the work would need more logic steps than the plan-size target (the operating profile; default 4) and BACKLOG does not already hold its parts, the planner splits — parts cut by tryable outcome (each ends in something that runs and can be tried), never by layer — 2–3 plans, each "part k of n of F<n>": goal / done-when subset / expected files / depends-on / size; it plans the first part (or the part named in the request, or the next part whose depends-on are shipped) and records the other parts as BACKLOG items — recording only (title, value, completion criteria from the section, size, dependencies, `spec: F<n>`; priority "undecided — next /backlog"), no prioritizing — noted as /parallel candidates only if expected files are disjoint and depends-on is empty. Make the plan reference the charter, CLAUDE.md, BACKLOG and ASSESSMENT/REBUILD_PLAN when they exist.
2. Have team-critic review every plan — pass the plan path and, when one exists, the section ID (from the argument, the BACKLOG item's `spec:` field or the planner's report). On REVISE, pass the findings verbatim to the planner (max 2 rounds, per the critic loop). A blocker only the CEO can settle goes to the CEO at once (AskUserQuestion) instead of spending a round.
3. If any item meets the escalation criteria and neither docs/DECISIONS.md nor the spec section already decided it, ask the CEO with AskUserQuestion; decided items go in plan section 6 as "decided — per spec/DECISIONS", not re-asked. If a step needs a capability no role has (a permission boundary or a separate judge), say so and suggest `/recruit <gap>` in a sentence.
4. Approval is the critic's APPROVE (with the escalation answers in, when there were any). At the cap with findings still open, ask the CEO with one AskUserQuestion call — approve as is / stop here — with the remaining findings attached one line each; never approve past a blocker yourself. Once approved: write docs/STATUS.md (Plan: <path> · Branch: none yet · Shipped: — · Next actions: 1. `/run <path>`) and commit the plan yourself together with it and any spec, BACKLOG or DECISIONS change this command made (`docs(plan): NNNN-<slug>`, by path) — the plan file does not change during /run except through the `수정:` path, so this commit is final and worktrees can see it. Report in three lines — goal, steps (count and the proves lines), risk and section 6 — then, inside an iteration (`deliver`), continue with `run` via the Skill tool; otherwise suggest to the CEO in a sentence: "run `/run <path>`".
