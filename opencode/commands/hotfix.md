Hotfix: $ARGUMENTS

A hotfix is a change the CEO can state in one sentence whose check is obvious: a defect with a reproduction, a wrong string, configuration value or default, a dependency or version bump. It skips the intake, the plan file, the critic and the per-step verifier; it keeps the independent verdicts (team-verifier, one team-reviewer lens) and the merge gate. A request that needs a design decision, adds behaviour, or names a path under the rules file's "## Risk paths" is a plan: say so in one sentence — "run `/plan bug: …`" (or `/plan <item>`) — and stop.

0. Branch. If the current branch is already hotfix/<slug> with a commit (the board's Plan line names it), continue from step 3. Otherwise apply the branches-and-sync rule (on main, synced), then `git switch -c hotfix/<slug>` yourself (slug: two to four words from the request). Write the board's Now block yourself: `Plan: hotfix — <the request in one line> · Branch: hotfix/<slug> · Shipped: —`, `Step: none`.
1. Implement. One team-implementer call with the request verbatim: the change; a regression test when it fixes logic (a string, configuration or version change needs none); the quick verification from AGENTS.md's Commands section; one commit `fix(<slug>): <summary>` whose body quotes the request (there is no plan file — the commit carries the why); a report naming the files touched and `git diff --stat main..HEAD`. If the implementer finds that the change needs a design decision or adds behaviour, it stops without committing and says why: `git switch main` yourself, leave the branch to the CEO, and suggest `/plan` in a sentence.
2. Cap. Over 3 files or 50 changed logic lines (tests excluded), or a file of `git diff --name-only main..HEAD` matching a Risk-paths glob: stop before the review. Ask the CEO with the question tool (proceed as a hotfix — the label becomes risk:high / plan it instead — the default), record it on the board (Waiting on CEO), and end the turn; the commit stays on hotfix/<slug>. "Proceed" continues at step 3; "plan it" means `/plan bug: … (commit on hotfix/<slug>)` in a new turn — the planner may reuse the commit, and the CEO deletes the branch once that plan has shipped.
3. Verify. team-verifier, full verification (the quick run was the implementer's own). On FAIL, add one to the board's `verifier FAIL` count and pass the report verbatim to team-implementer to fix and commit; team-verifier confirms (max 2 rounds; past that, stop and report to the CEO). Record `Last verifier: PASS full @<hash>`.
4. Review. One team-reviewer, correctness lens, diff range main..HEAD (a hotfix that would need the security lens has hit a Risk path and stopped at step 2). Blocker/major findings: record them under the board's Open review findings and add their number to `review blockers`; team-implementer fixes, team-verifier confirms (quick), re-review only the fix diff (max 2 rounds; past that, stop and report). On APPROVE set Open review findings to `none`.
5. Ship (the reduced /ship). Resolve the merge policy as /ship does — the AGENTS.md "## Merge policy" override, else `git remote` empty → local; a remote with `gh repo view --json autoMergeAllowed -q .autoMergeAllowed` true and a protected default branch with required checks → auto-low-risk; anything else → manual — and report the verdict in one line. Label `risk:low`, or `risk:high` when the CEO chose "proceed" at step 2. Write the PR description: the request / files touched and diff size / verification evidence (commands and results) / the review result / rollback (`git revert <commit>`). One team-implementer call (pass it the description, the label and the verdict): add the CHANGELOG line when the project keeps one and the docs/METRICS.md line — date / `hotfix:<slug>` / logic diff lines / verifier failures, review blockers and CEO questions from the board's Counts line / acceptance `n/a` / request→ship duration — and commit them as `docs(<slug>): ship` (when the verdict is local, also docs/prs/hotfix-<slug>.md holding the description); then per verdict: **manual** and **auto-low-risk**: `git push -u origin hotfix/<slug>` and `gh pr create --title "<summary>" --body "<description>" --label risk:<value>` — never `gh pr merge --auto`: the PR is the CEO's one look at the diff; **local**: nothing more. Never push to main directly.
6. Gate. **local**: ask the CEO for merge approval with the evidence summary (the merge gate; not counted); on approval `git switch main && git merge --no-ff hotfix/<slug>` and `git branch -d hotfix/<slug>` yourself. **manual** and **auto-low-risk**: `git switch main` yourself and tell the CEO in one line to read the diff and merge the PR before the next /plan.
7. Board: keep the Plan line (`hotfix — …`) with its branch and set Shipped: PR <link> or merge <hash>; Step: none; Next actions: 1. read the diff and merge the PR (omitted for local), 2. `/plan <next BACKLOG item>`. End here; a hotfix never starts /run.
