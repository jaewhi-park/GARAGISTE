Make or revise the product brief, docs/BRIEF.md. Input: $ARGUMENTS

Load the `brief` skill first (template, slots, writing rules, report line). The brief is product level only — what is being built, for whom, what is in and out, how success is measured. Feature detail (a flow, a screen, an API) belongs to /plan's spec rounds: when the CEO starts designing one, say so in a sentence, keep one line for the brief's appendix, and continue.

0. If AGENTS.md has no "## Language" section, first ask the CEO the working language with the question tool (options: ko / en / other; default: the language of the CEO's message, or of the file when the input is a file), run `node .opencode/scripts/set-language.mjs <code>`, and continue in that language. Skip when it is already set.
1. Mode — from the injected board and the input (the only file read allowed here is a grep of docs/BRIEF.md's `Status:` and `Kind:` lines):
   - board `Brief: … · brainstorm (checkpoint k)` → have team-planner report the whiteboard (decided / later / rejected / open) and continue the brainstorm from there (step 2).
   - board `Brief: … · draft | correction k` → have team-planner report the open slots and continue at step 3.
   - docs/BRIEF.md with `Status: approved` or `revised` → revision mode: say so in one sentence and ask what changed; the whiteboard is kept on top of the existing brief (step 2), and the compile writes only the differences.
   - the input names an existing file, or is pasted text longer than a few lines → entrance B: hand it to team-planner (the path, never the contents; pasted text verbatim) to normalize into docs/BRIEF.md per the template, keeping the CEO's wording, `Source:` = the path; the original stays untouched and is linked, never pasted. Tell the CEO they can keep talking (step 2) or go straight to step 3.
   - otherwise (an idea, or nothing) → entrance A, step 2.
2. Brainstorm — brainstorm mode (team-lead principles): no agenda and no slot list. The CEO throws ideas; you propose, push back, sketch alternatives and name costs, at length when useful. Keep a whiteboard in your head: decided / later / rejected with the reason / open. Every ten or so exchanges — and always before a /handoff or when compaction looms — checkpoint it: one team-planner call with the CEO's messages verbatim and each of your proposals the CEO accepted, quoted, in order; the planner appends them to docs/BRIEF.md under "## Whiteboard" (`Status: whiteboard`) and reports the brief line; update docs/STATUS.md yourself (`Brief: docs/BRIEF.md · brainstorm (checkpoint k)`, next action `/brainstorm`). The brainstorm ends when the CEO asks for the document ("기획서 만들어줘", "정리해줘", "write it up", or the like); a CEO who opens with a full description and asks for the document at once skips straight to step 3.
3. Compile — one team-planner call with every fragment since the last checkpoint verbatim. Create mode: the planner rewrites docs/BRIEF.md per the template, sorting ideas into decided / later / rejected (with the reason), keeping feature sketches as one line each in the appendix and moving a requirement list with IDs into docs/BACKLOG.md (`req:` items; the brief keeps a pointer). Revision mode: only the differences, a Revision-history line, and the charter lines the change touches. Either way the planner reports the brief line with the slots still Open — never filled with a guess. Update the board (`draft`).
4. Open slots — ask only what the report lists as Open, in plain chat, one numbered message (typically: a measurable success metric, three concrete non-goals, the kill criterion, constraints, the deadline, an item the planner flagged). Answers may arrive in several messages (the spec skill's rules: acknowledge in one line, close on "여기까지" / "됐다" / a question back, or when every slot is answered); then one planner call with the fragments verbatim. "Your call" becomes `undecided — planner default: <x>; confirm at the /kickoff ADR question` (or `at the /assess strategy question`).
5. Pre-mortem — have team-critic review docs/BRIEF.md (revision mode: also docs/CHARTER.md and the board's Plan line) per its brief checklist. Every finding on a brief is for the CEO: present them in plain chat, one line each with the planner's default, as the correction round; the CEO answers; one planner call with the answers verbatim; board `correction k`. Max 2 correction rounds (per the critic loop); what is still disputed goes under Undecided. Skip the critic only when the CEO says so.
6. Approval — one question-tool call: approve / correct (the CEO reads docs/BRIEF.md and corrects in plain chat, the planner revises, ask again — counts toward the 2 corrections) / stop here (stays draft; nothing is committed; the board keeps `draft`). On approve:
   - team-planner sets `Status: approved <date>` — in revision mode `revised <date>`, applying the charter edits it listed and keeping docs/CHARTER.md under 60 lines;
   - team-implementer commits by path — docs/BRIEF.md, docs/BACKLOG.md when seeded, docs/CHARTER.md when revised, docs/README.md, AGENTS.md (its Language section), .gitignore whenever it is untracked or its `docs/STATUS.md` line is uncommitted (add the line when the installer did not), and .opencode/ and opencode.json if not yet tracked — as `docs(brief): <title> — approved` on main (branches-and-sync rule) or, for a revision, `docs(brief): revised — <summary>` on the current branch;
   - write docs/STATUS.md (Now: `Brief: docs/BRIEF.md · approved · Kind: <kind>` — after a revision, the existing Plan line stays; Next actions: 1. `/kickoff` for Kind 신규, `/assess <path>` for Kind 레거시, `/backlog` after a revision) and end by suggesting that command in one sentence — in a new session when the brainstorm was long. Do not start it yourself.
