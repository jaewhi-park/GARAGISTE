Ship. Target: $ARGUMENTS

1. If docs/STATUS.md records `Last verifier: PASS full @<hash>` and `<hash>` equals `git log -1 --format=%H` — or every commit since it touches only docs-only files (`git diff --stat <hash>..HEAD`) — reuse that verdict as the evidence. Otherwise run full verification with team-verifier (all commands in AGENTS.md; include the parity harness for legacy) and record the hash. On FAIL, go back to the /build loop.
2. **Resolve the merge policy automatically.** If AGENTS.md "## Merge policy" has an explicit value, use it (override; with no remote an `auto-low-risk` override still resolves to **local**, only without the approval question for `risk:low`); otherwise derive it from repository state:
   - `git remote` is empty → **local**
   - a remote exists, `gh repo view --json autoMergeAllowed -q .autoMergeAllowed` is true, and the default branch has a protection rule with required status checks (check `gh api repos/{owner}/{repo}/branches/<default>/protection` or `gh api repos/{owner}/{repo}/rules/branches/<default>`) → **auto-low-risk**
   - anything else (remote without protection/auto-merge, or no `gh`) → **manual**
   Report the verdict and its reason in one line, e.g. "manual — remote exists, no branch protection. Enabling protection + auto-merge on main would switch to auto-low-risk". Lead-merge applies on top of the verdict: a `risk:low` plan with full verification PASS and every lens APPROVE is merged by the lead — local: `git merge --no-ff` without asking; manual: `gh pr merge --squash` (`--merge` for integrate/*) once required checks are green (`gh pr checks <branch> --watch`; no checks configured counts as green); auto-low-risk: `gh pr merge --auto --squash`. `risk:high` is the CEO's merge.
3. Write the PR description: **Proven** first — one line per `proves:` line of the plan, `<test name> — red: <k> failing → green`, taken from the implementers' Proven lines (an `n/a` with its reason), then the exact command that runs those test files (AGENTS.md's run-one-test-file command with the files, or the quick verification when it runs them all) so the CEO can run them; then summary / verification evidence (commands and results) / review findings and how they were handled / risks and rollback / decisions needed from the CEO — and, when the plan is user-facing (its spec section has Screens and states, its steps touch a UI, CLI output or public API, or the CEO asked), a "Try it" section: the run command from AGENTS.md's build/run line and 3–5 numbered steps (the screens the steps' `shows:` lines name) taken from the spec's core flow or the plan's completion criteria, each ending in something the CEO can see. Set the risk label: `risk:high` when `git diff --name-only main..HEAD` hits a "## Risk paths" glob of the rules file, when the plan's `Risk:` header says high, or when an item of the Escalation section or the rules file's "Additional escalation items" was touched; otherwise `risk:low`. You may raise the label, never lower a Risk-paths hit. For an integration branch (integrate/<date>, from /integrate), one summary block per integrated plan and the highest risk label among them.
4. team-planner only when a docs/ judgment is owed: the plan references a spec section (update the section's Status line — `done` when every Done-when line is covered by a shipped plan: shipped plans are the `(F<n>)` lines in docs/METRICS.md plus the line about to be appended; otherwise keep `in progress — plans: …` and append `remaining: <uncovered Done-when lines>`), or an ADR or docs/DECISIONS.md must change. One call; it does not commit. A plan without a section, ADR or decision to record skips this step.
5. One team-implementer call (pass it the PR description, the risk label, the verdict, the board's Counts line, the logic diff size from /review and the Proven lines): append the docs/METRICS.md line — for an integration branch, one line per integrated plan, named by the plan paths on the board's Parallel-in-progress list (the merge commits on integrate/<date> name them too) — date / slug (`<plan-slug> (F<n>)` when section-backed, `(req <ID>)` when the plan's Source carries one, `rev n` when the plan was amended) / logic diff lines / tests `+<n>` (Proven lines that went red → green) and `n/a <m>` / verifier failures, review blockers and CEO questions taken from the board's Counts line (brief slots, revision discussions and the merge gate are expected and not counted) / acceptance: `try-it` when the PR carries a "Try it" section, else `n/a` (a later `bug:` plan naming this slug is the failed outcome /retro looks for) / plan-approval→ship duration (/retro reads this file); when the verdict is local, also save the PR description as docs/prs/NNNN-<slug>.md (an integration: docs/prs/NNNN-integrate-<date>.md); update CHANGELOG and user docs; commit them together with the planner's uncommitted docs changes (`docs(<slug>): ship`; an integration: `docs(integrate-<date>): ship`), tidy commits, then per verdict:
   - **manual**: `git push -u origin <branch>` and, unless `gh pr view <branch>` already shows an open PR (report that one), `gh pr create --title "<summary>" --body "<PR description>" --label risk:<value>` (without `gh`, push only and report body and command). Then, for `risk:low`, merge as lead-merge says; report the PR link (merged, or waiting on the CEO for `risk:high`).
   - **auto-low-risk**: the same, plus `gh pr merge --auto --squash` (`--merge` for an integrate/* branch, so each plan keeps its merge commit) when `risk:low` (GitHub merges once required checks pass); for `risk:high` report the link only — the CEO reads the diff and merges. A "Try it" section never blocks a merge: main is always runnable and the CEO tries the product from main (the board's Tryable now).
   - **local**: nothing more.
   Never push to main directly.
6. **local** only: `risk:low` → merge without asking (lead-merge); `risk:high` → ask the CEO for merge approval with the evidence summary (the merge gate; not counted) and on approval run `git switch main && git merge --no-ff <branch>` then `git branch -d <branch>` yourself (<branch> = the plan/<slug> or integrate/<date> branch being shipped; for an integration also the plan/* branches the board lists as merged into it).
7. **manual** and **auto-low-risk**: `git switch main` yourself (in a linked worktree stay on the worktree branch; the plan branch keeps its PR; the next command's sync pulls the merge in) then, when you merged the PR, `git fetch origin && git merge --ff-only origin/main` (after a squash merge, the rebase of the branches-and-sync rule); for `risk:high` record the PR under Waiting on CEO and tell the CEO in one line that it waits for their merge.
8. Update docs/STATUS.md yourself: keep the Plan line with its Branch (an integration: clear the Parallel-in-progress list once Shipped is set) and set Shipped: PR <link> (manual, auto-low-risk; `PR pending — <branch> pushed` when the CEO opens the PR themselves) or merge <hash> (local); Step: none; add the plan's tryable outcome to the board's Tryable now (the "Try it" steps when the PR has them); Next actions: 1. merge the PR (`risk:high` only — Waiting on CEO), 2. the next backlog item (inside an iteration, `deliver` continues). Then commit the board by path — `docs(status): <slug> shipped` — on the branch you are on (main after step 7; in a linked worktree the board is the main checkout's: skip it).
