Start a new project from the approved product brief. Note: $ARGUMENTS

The brief's approval was the CEO's "go": from here the team decides and logs; the CEO answers one question (the stack — the most expensive decision to reverse — and the budget) and anything on the escalation list, nothing else. This command writes documents only — no code, no verifier: the scaffold is the first step of plan 0001 and goes through the normal build → review → ship loop in iteration 1. It decides what is expensive to reverse and defers the rest to the plan that first needs it: the spec sections are written at /plan (the `spec` skill's Extending rule), the design foundation by the first UI plan after the skeleton, the security baseline's remaining lines by the first Risk-path plan. Every step is re-entrant: an output that already exists (the file, the commit) is skipped.

0. Precondition: docs/BRIEF.md with `Status: approved` or `revised` and `Kind: 신규` (from the injected board's Brief line, else Grep those two lines — the one file read allowed here). If there is none, or it is still whiteboard or draft, say so in one sentence — "run `/brainstorm <idea, or the path of a document you wrote>` first" — and stop; with `Kind: 레거시`, say so and suggest `/assess <path>` instead. If AGENTS.md has no "## Language" section (a brief committed from elsewhere), ask the CEO the working language with the question tool (options: ko / en / other; default: the language of the brief), run `node .opencode/scripts/set-language.mjs <code>`, and continue in that language.
1. One team-planner call (name the `charter`, `design` and `security` skills — it reads them): (a) derive docs/CHARTER.md from docs/BRIEF.md per the `charter` skill (under 60 lines, `Source: docs/BRIEF.md`; a slot the brief leaves undecided gets the planner's default with the reason and a docs/DECISIONS.md line — never a guess presented as fact); (b) write docs/adr/0001-stack.md, `Status: proposed`, its Context taken from the brief's constraints and risks — when the brief's Constraints name the stack, the decision and its reason, no alternatives table; otherwise 2–3 stack/architecture alternatives and a recommendation — with two short sections: "Design foundation", one line naming the component library or primitives when the brief has a UI (tokens, shell and the screenshots command are the foundation step's, in the first UI plan after the skeleton — the `design` skill), and "Security baseline" per the `security` skill, deciding only the lines the scaffold carries (secrets out of the repository, the stack's standard protections, the audit command, the lockfile) and marking every other line `decided at the first Risk-path plan` or "not applicable — <why>". No critic here: it reviews the ADR in step 3 together with the index and the plan. Then the one question-tool call of this command: the stack (the brief's, to confirm, or else the planner's recommendation first with its reason), the budget tier (unlimited = API/in-house / high = Max 20x / medium = Max 5x / low = Pro), and any brief Undecided item that meets the escalation criteria (paid services, security or user data, a non-goal conflict) with the planner's default — every other Undecided item is the planner's default, logged. The answers go to the planner verbatim in step 2 and to `hire` in step 4.
2. Two team-planner calls in one turn, in parallel, each with the step-1 answers verbatim:
   - Rules and decisions (name the `agents-md` skill): (a) write AGENTS.md per the `agents-md` skill — "## Commands" holds the chosen stack's standard commands (setup, quick and full verification, the run-one-test-file form, build/run, the audit command in full verification — no `screenshots:` line: the design-foundation step registers it), each ending in ` — unverified` until team-verifier has run it (the /assess convention: the full verification at the end of plan 0001's build removes the marker); "## UI paths" seeded from the stack's conventional screen, component and style paths when the brief has a UI, and "## Risk paths" from the security baseline — the migration, schema, auth and public-API paths this stack has — with its dependency manifests and CI/deploy config under "## Risk paths (live)", which count once the product is live; (b) set docs/adr/0001-stack.md to `Status: accepted` with the CEO's choice and record the step-1 answers and every default in docs/DECISIONS.md (and the brief's Undecided list).
   - Spec index, backlog and the first plan (name the `spec` skill): (c) write the docs/SPEC.md index per the `spec` skill — a row for every Decided line of the brief, each `Status: pending`, File `—`, no section file: /plan writes it when the row's turn comes (the Extending rule), from the Decided line and the appendix — and report the spec report line; (d) write docs/BACKLOG.md — one item per index row (`spec: F<n>`; completion criteria = the brief's Decided line, marked `pending section`), Later lines as P2, Non-goals under "Excluded"; when /brainstorm already seeded docs/BACKLOG.md from a requirement list, keep those items and add only what is missing — and docs/plans/0001-walking-skeleton.md, `Source: docs/BRIEF.md core flow (walking skeleton)`, sections 1–2 the brief's demo scene as completion criteria and its Non-goals: step 1 is the scaffold (kind: scaffold — the stack per the ADR, the security baseline's scaffold lines, the test runner wired into the quick verification and one smoke test that asserts something about the skeleton; no shell, tokens or screenshots command; its verification command is the rules file's quick verification), then at most two logic steps — the thinnest end-to-end slice of the brief's core flow, each with its `proves:` lines, a UI step with `shows: n/a — no design foundation yet`; section 5 says the plan is slower for the harness step.
3. Have team-critic review, in one call, target `kickoff`: the stack ADR, the docs/SPEC.md index and the walking-skeleton plan (the first plan is always reviewed) — with the facts block of the `plan` skill's critic call (here: no test harness yet, plan 0001's step 1 is it; Stage pre-launch; the index rows; the planner's spec report line; the charter's Non-goals and Constraints pasted). Findings go to the planner verbatim, one round; the critic reads again only when a blocker was among them (the changed sections, fixed | stands) — majors and minors close on the planner's report; a finding only the CEO can settle — an escalation item — goes to the CEO at once with the question tool, default attached. The critic's APPROVE on the plan is its approval; with a blocker still standing, one question-tool call — approve as is / stop here.
4. Commit the files this command wrote yourself, by path — docs/CHARTER.md, docs/adr/0001-stack.md, docs/SPEC.md, docs/BACKLOG.md, docs/plans/0001-walking-skeleton.md, docs/DECISIONS.md, docs/BRIEF.md if changed, AGENTS.md, docs/README.md, docs/STATUS.md, .gitignore if untracked, and .opencode/ and opencode.json if not yet tracked — on main, as `docs(kickoff): charter, stack ADR, spec index, backlog, plan 0001`. Write docs/STATUS.md (`Mode: running` · Stage: pre-launch · Run: not yet (the AGENTS.md build/run line once plan 0001 ships) · Iteration 1 · Plans: docs/plans/0001-walking-skeleton.md — · ends: 0001 shipped — the first iteration is the skeleton alone, so the CEO sees it before anything is built on it · Now: none · Next actions: 1. `/hire` in this session 2. `deliver` — iteration 1, in a new session) and commit it by path (`docs(status): kickoff done`). End with one report — the index rows (F1–F<n>, one line each, all pending), plan 0001's steps, what was decided by default (a pointer to docs/DECISIONS.md) — and a sentence suggesting `/hire` with the budget tier from step 1 (it applies without a second question and shows the roster), then a new session and 계속 (model assignments load at session start; the board's Mode makes that session continue by itself). Do not start the iteration in this session.
