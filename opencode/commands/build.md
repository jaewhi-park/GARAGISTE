description: Implement an approved plan step by step (the implementer proves each step red → green; the verifier gives the full verdict at the end)
agent: team-lead
---
Execute the approved plan: $ARGUMENTS (plan file path)

0. Read the plan file (it is short). If the current branch is already plan/<slug> (a /spawn worktree, or the board names it), stay on it and continue from the step after the last PASS the board records (a plan amended with `Revised: <date> (from step k)` continues at step k — the steps before it are unchanged and already committed; a header still marked `draft` is not approved: stop and say so) — or, without a board, after the last step commit on the branch (`git log --format=%s%n%b main..HEAD` names plan and step); step 1 when there is neither. In a linked worktree on any other branch, stay on it too — the branch was cut when the worktree was made. Otherwise, on main: apply the branches-and-sync rule (synced), make sure the plan file is committed (`git status --porcelain <plan path>` prints nothing; if not, team-implementer commits it as `docs(plan): NNNN-<slug>` first), then `git switch -c plan/<slug>` yourself (slug from the plan filename). If that branch already exists locally or as origin/plan/<slug>: `git switch plan/<slug>` when its PR is not MERGED (`gh pr view plan/<slug> --json state -q .state`, or no remote) — an abandoned earlier run continues there; when it is MERGED, stop and ask the CEO to delete it first. One plan = one branch. Record the plan and branch in docs/STATUS.md (Shipped: —).

For each step, in order (steps of one plan never run in parallel; only whole independent plans do, via the CEO's /spawn):
1. Assign exactly that step to team-implementer, naming the plan file path and step number and quoting the step's lines — its `proves:` lines included.
2. Check the report for format only, no judgment: every `proves:` line of the step has a `Proven:` line with red → green (or the plan's `n/a — <reason>`), and every quick-verification command is listed at exit 0 (or `docs-only`). An incomplete report goes back to the implementer with the missing line named (max 3 rounds; past that, stop and report to the CEO). team-verifier runs quick verification per step only when AGENTS.md's "## Operating profile" says `per-step verifier: on`, the plan's `Risk:` header says high, or the plan is legacy work (a rebuild step, a parity harness); on FAIL, add one to the board's `verifier FAIL` count and pass the failure report verbatim to the implementer to fix (max 3 rounds; past that, stop and report to the CEO).
3. Record the step on the board's Step line yourself — state and `Last verifier: proven (self-check)`, or `PASS quick` when the verifier ran — and move to the next step.

When all steps are done, run full verification with team-verifier — the independent verdict on the whole plan. On PASS, record `Last verifier: PASS full @<hash>` (`git log -1 --format=%H`) in docs/STATUS.md so /ship can reuse it. On FAIL, add one to the board's `verifier FAIL` count and pass the report verbatim to team-implementer together with the plan's step list (it locates the step by commit, fixes and commits); team-verifier confirms with full verification (max 3 rounds; past that, stop and report to the CEO). Then suggest `/review` to the CEO in a sentence — except in a /spawn worktree session (the directory is not the first line of `git worktree list`): there, end with "close this session and run `/integrate` in the main session" — the branch is reviewed, merged and shipped from there, never from the worktree.
