description: Default path — take an approved plan through build → review → ship. Stops only at escalation, fix-loop overflow and merge approval
agent: team-lead
---
Take the approved plan all the way: $ARGUMENTS (plan file path)

Stop only at three places: an escalation question, a fix loop exceeding 3 rounds, and merge approval (when the policy resolves to local/manual). Otherwise proceed without asking the CEO, and report once at the end in the final report format.

1. Branch (= /build step 0): read the plan file. If the current branch is already plan/<slug> (a /spawn worktree, or the board names it), stay on it and continue from the step after the last PASS the board records (a plan amended with `Revised: <date> (from step k)` continues at step k — the steps before it are unchanged and already committed; a header still marked `draft` is not approved: stop and say so) — or, without a board, after the last step commit on the branch (`git log --format=%s%n%b main..HEAD` names plan and step); step 1 when there is neither. In a linked worktree on any other branch, stay on it too — the branch was cut when the worktree was made. Otherwise, on main: apply the branches-and-sync rule (synced), make sure the plan file is committed (`git status --porcelain <plan path>` prints nothing; if not, team-implementer commits it as `docs(plan): NNNN-<slug>` first), then `git switch -c plan/<slug>` yourself (slug from the plan filename). If that branch already exists locally or as origin/plan/<slug>: `git switch plan/<slug>` when its PR is not MERGED (`gh pr view plan/<slug> --json state -q .state`, or no remote) — an abandoned earlier run continues there; when it is MERGED, stop and ask the CEO to delete it first. One plan = one branch. Record the plan and branch in docs/STATUS.md (Shipped: —).
2. Implement (= /build): per step, in order, assign it to team-implementer with plan path, step number and the step's lines (its `proves:` lines included), then check its report for format only — every proves line has a `Proven:` line with red → green (or the plan's `n/a`), every quick command at exit 0; an incomplete report goes back to the implementer (max 3). team-verifier runs per step only when the operating profile says `per-step verifier: on`, the plan is risk:high or it is legacy work (a rebuild step, a parity harness); on FAIL, bump the board's `verifier FAIL` count and pass the report verbatim for a fix (max 3). Record the step on the board (`proven (self-check)` or `PASS quick`) and continue. After the last step, full verification with team-verifier — the independent verdict — and record `PASS full @<hash>` in STATUS.
3. Review (= /review): the test-file floor first — a logic commit whose step has proves lines other than `n/a` but touches no test file (`git show --name-only`) stops here: report the step to the CEO, no reviewer spawned. Then 2 lenses (correctness, security), or 4 for risk:high / over 600 logic lines / hot paths, in parallel, each given the diff range and the proves lines → collect blocker/major → implementer fixes → verifier full, `PASS full @<hash>` recorded (max 3) → re-review only the fix diff with the lenses that objected → all APPROVE.
4. Ship (= /ship): reuse the recorded full PASS if HEAD is unchanged or only docs-only files changed since, else full verification → merge-policy resolution (local / manual / auto-low-risk) → PR description ("Proven" first: each proves line's test, red → green, and the command that runs them; a "Try it" section for user-facing plans) + risk label → a planner call only when a spec Status line, an ADR or DECISIONS must change → one implementer call (METRICS line with `tests +n`, CHANGELOG, user docs, docs/prs if local, commit incl. the planner's files, tidy, push / PR / auto-merge per verdict — never auto-merge a PR with a "Try it" section) → local merge after CEO approval (a PR with a "Try it" section asks: approve and merge / I will try it first — board: Waiting on CEO / problem found → `/plan bug:`, no merge), or `git switch main` after the PR is created (manual / auto-low-risk; in a linked worktree stay on the worktree branch; the plan branch keeps its PR) → update STATUS (Plan line kept, Shipped: PR link or merge hash · Step: none · next: try it when the PR has a "Try it" section and merge, then `/plan <next BACKLOG item>`) → tell the CEO in one line to merge before the next /plan — after walking the "Try it" steps when the PR has them.
