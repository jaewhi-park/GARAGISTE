# GARAGISTE 사용 가이드 — opencode 판

> 영어 정본: [GUIDE.md](GUIDE.md). 에이전트 프롬프트는 영어이며, 응답·질문·문서 언어는 규칙 파일(AGENTS.md / CLAUDE.md)의 `## Language` 줄로 정합니다(`/brainstorm` 시작 시 한 번 묻고, `/lang <code>`로 언제든 변경). 비어 있으면 당신이 쓰는 언어를 따릅니다.


이 문서는 사람(당신)을 위한 것이다. 팀이 무엇을 하는지가 아니라 **당신이 언제 무엇을 해야 하는지**만 적는다.
설정 파일의 의미는 README.md, 산출물의 위치는 docs/README.md 를 본다.

## 0. 한 장 요약

당신의 일은 넷이다. **결정한다 / 증거를 읽는다 / 품질 기준을 정한다 / 머지한다(정책대로).**
그 외는 팀이 한다. 당신은 코드를 치지 않는다(오타 수준 제외). 대신 데이터·인터페이스·보안을 건드린 diff는 직접 읽는다.

| 상황 | 명령 | 당신이 하는 것 한 줄 |
|---|---|---|
| 기획서 | `/brainstorm <아이디어 또는 파일>` | lead와 자유롭게 브레인스토밍하거나 직접 쓴 문서를 내고, 빈 슬롯과 사전 부검에 답하고, 기획서를 승인. 피벗이면 다시 실행 |
| 새 프로젝트 | `/kickoff` | 승인된 기획서가 필요. 도출된 헌장 줄과 스택 ADR을 확인 |
| 레거시 인수 | `/assess <대상>` | 승인된 기획서가 필요. "버그로 보이는 동작"의 보존/수정 방침, 리빌드 전략 승인 |
| 할 일 정리 | `/backlog [아이디어]` | 상위 3개 순서만 확정 |
| 설계 | (`/plan` 안에서) | ADR의 "대안"과 "결과"를 읽고 되돌릴 수 있는지 확인 |
| 단일 개발 | `/plan <항목>` → `/run <계획>` | 접수 질문 한 번에 답하고(또는 "완료 조건"을 직접 적고), 계획 승인 한 번, 게이트 질문에만 답, 손 떼기 |
| 복잡한 기능 | `/plan <항목>` → 접수에서 "사양서 예" | 2~3라운드에 당신 말로 답하고, 사양서 승인, 그다음 계획 승인 |
| 병렬 개발 | `/spawn <계획들>` → 각 세션 `/build` → `/integrate` → `/ship` | 파일 집합이 겹치지 않는지 확인, 통합 순서 결정 |
| 리뷰 | (`/run` 안에서) 또는 `/review` | 충돌하는 지적만 판정 |
| QA | (verifier 자동) + PR의 "직접 확인" 단계 | 초록불이 아니라 실행한 명령과 실패 개수를 읽기. 머지 전에 직접 확인 단계를 밟기 |
| 디버깅 | `/plan "버그: … 재현 테스트 먼저"` | 재현 조건을 최대한 구체적으로 주기 |
| 작은 수정 | `/hotfix <무엇을 왜>` | 확인 방법이 자명한 한 문장(재현 있는 버그, 잘못된 문구·설정·기본값, 버전 올리기); diff를 읽고 머지 — 설계 판단이 필요하면 `/plan` |
| 변경 요청 | 멈추라고 말하고 `/plan <사양서 또는 계획 파일> 수정: <바뀐 것>` | 이야기하고, "정리해줘"라고 하고, 개정을 승인. 진행 중 계획은 같은 브랜치에서 이어진다 |
| 트러블슈팅 | 3회 규칙, 세션 폐기 | 팀이 헛돌면 고치지 말고 끊기 |
| 병합 | `/integrate` / `/policy` | 로컬 통합은 팀. main 머지는 자동 판정(local / manual / auto-low-risk) |
| 출하·릴리즈 | `/ship` → `/release` | PR의 검증 증거 읽기, `risk:high`면 diff 직접 보기 |
| 세션 종료 | `/handoff` | 도중에 멈출 때만. 보고의 "다음 세션 첫 행동"이 맞는지 확인 |
| 세션 재개 | `/resume` | 상태판이 있을 때만(주입된 파일을 보면 안다). 상태판과 저장소가 어긋나면 저장소 편 들기 |
| 회고 | `/retro <대상>` | 규칙 한 줄만 승인, 나머지는 거절 |
| 채용 | `/hire` | 예산 티어·성격 질문에 답하고 배정표 승인 (kickoff/assess 직후) |
| 팀 점검 | `/roster` | 모델·권한 배정 확인 |
| 언어가 틀릴 때 | `/lang <code>` | `/brainstorm` 시작 시 한 번 묻고, 언제든 변경 |
| 역할이 비어 있을 때 | `/recruit <gap>` | 새 권한 경계나 별도 판단자가 필요할 때만. 지식 부족은 스킬로. 모델은 로스터에서 가져오므로 /hire 재실행 불필요 |

## 1. 설치와 첫 실행

설치 위치는 세 가지 중 하나. 저장소 루트의 진입점에 대상(opencode)을 먼저 준다:
```
./install.sh opencode                       # 현재 경로(가 속한 git 레포 루트)
./install.sh opencode -Project <경로>       # 그 경로에 설치 (--project 도 됨)
./install.sh opencode -Global               # 전역
.\install.ps1 opencode -Project <경로>      # Windows PowerShell — 옵션 표기는 동일
```
`opencode/install.sh` 를 직접 실행해도 같다(대상 인자 없이).
- 경로가 레포의 하위 폴더면 git 루트로 올라가 설치하고 알려준다. git 저장소가 아니면 `git init` 을 제안한다.
- --global  → ~/.config/opencode (모든 레포). 전역 설치는 프로젝트의 .gitignore를 건드릴 수 없으니 `docs/STATUS.md`는 직접 추가한다(잊으면 첫 이정표 커밋이 추가한다).

**Windows 실행 정책**: `.\install.ps1` 이 "스크립트를 실행할 수 없으므로" 로 막히면 둘 중 하나.
- 한 번만: `powershell -ExecutionPolicy Bypass -File .\install.ps1`
- 영구(권장): `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` 후 `Unblock-File .\install.ps1` (인터넷에서 받은 파일 표식 제거)

**Windows 한글 깨짐**: 셋 중 어디서 깨지는지에 따라 다르다.
- `install.ps1` 출력만 깨진다 → 스크립트 인코딩 문제. 이 번들의 .ps1 은 UTF-8 BOM 으로 저장돼 있어 Windows PowerShell 5.1 에서도 정상이다. 직접 편집했다면 BOM 있는 UTF-8 로 저장.
- 터미널 전반(claude/opencode 출력, git log)이 깨진다 → 콘솔 인코딩. `$PROFILE` 에 다음 두 줄을 넣는다: `[Console]::InputEncoding = [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)` / `$OutputEncoding = [Console]::OutputEncoding`. 임시로는 `chcp 65001`.
- 글자가 □ 로 나온다 → 폰트. Windows Terminal 을 쓰고 한글 글리프가 있는 폰트(D2Coding, Sarasa Mono K, 또는 fallback 이 되는 Cascadia)로 설정. 옛 conhost + 래스터 폰트는 한글을 못 그린다.
- 근본 해결: Windows 설정 → 시간 및 언어 → 언어 → 관리 언어 설정 → 시스템 로캘 변경 → "Beta: 세계 언어 지원을 위해 Unicode UTF-8 사용" 체크(재부팅). 시스템 코드 페이지가 65001 이 된다. 일부 오래된 한국어 프로그램이 깨질 수 있으니 그런 게 있으면 위 프로필 방식으로.

**배치 권장**: 템플릿 zip 은 프로젝트 밖(예: `~\garagiste`)에 풀고, 프로젝트 루트에서 `& ~\garagiste\install.ps1 opencode -Project .` 처럼 호출한다. 프로젝트 안에 직접 풀어도 동작하지만(설치 스크립트가 감지해 복사를 건너뜀) 템플릿의 README.md 가 프로젝트 README 자리를 차지한다.

**git 저장소가 아닌 폴더**: 팀은 브랜치·커밋·worktree 를 전제로 한다. 설치 스크립트가 `git init`(기본 브랜치 main)을 제안하니 수락하면 된다.

첫 실행: 레포에서 `opencode` → Tab 으로 `team-lead` 선택 → 먼저 `/brainstorm`(기획서), 그다음 신규면 `/kickoff`, 레거시면 `/assess`; 이어하기면 `/resume`.
확인할 것: planner가 docs/ 밖을 못 쓰고 docs/ 안은 쓰는지(edit 패턴은 루트 기준 상대 경로: `docs/*`, `**/docs/**`는 안 됨), 훅이 `git push --force`를 막는지.

### 모델·예산 — `/hire`
`/kickoff` 또는 `/assess` 가 끝나면 lead 가 `/hire` 를 제안한다. lead 가 사용 가능한 모델을 확인하고 당신에게 예산 티어(unlimited / high=Max 20x / medium=Max 5x / low=Pro), 프로젝트 성격, 병렬 계획을 묻고 역할 × 모델 표를 이유와 함께 내놓는다. 당신은 표를 승인하거나 한두 줄 바꾼다. 원칙: 판단하는 자리(planner·critic·reviewer)에 강한 모델, verifier 는 가장 빠른 모델, implementer 는 예산에 따라. 승인하면 스크립트가 model 줄만 바꾸고 AGENTS.md 에 "운영 프로필"이 남는다. 새 세션부터 반영. 설치할 때 `-Budget <티어> -Strong <id> -Fast <id>`를 주면 kickoff/assess 세션부터 verifier가 빠른 모델로 돌고, `/hire`가 그 위에서 다듬는다. 예산이 바뀌면 `/hire` 를 다시 하고, 현재 배정은 `/roster` 로 본다. 설치 스크립트의 `--budget` 은 판단 없이 기계적으로 배분하는 비대화형 경로다.

### 언어
에이전트 프롬프트는 영어다. 응답·질문·문서는 AGENTS.md의 `## Language` 줄을 따른다. 비어 있으면 `/brainstorm`이 처음에 묻고(`/kickoff`·`/assess`는 기획서를 다른 곳에서 가져와 커밋한 경우에만), `/lang <code>`로 언제든 바꾼다(스크립트가 그 절만 다시 쓴다). 비어 있을 때 에이전트는 당신의 마지막 메시지 언어를 따르지만, 영어 명령 템플릿 때문에 lead가 영어로 넘어갈 수 있다. 그러면 `/lang`을 실행한다.

## 2. 상황별 가이드

각 항목은 같은 틀이다: 언제 / 명령 / 팀이 하는 일 / **당신이 하는 일** / 승인 기준 / 흔한 실수.

### 2.1 프로젝트 기획 (신규)
- 언제: 레포가 비어 있거나 코드보다 아이디어가 먼저일 때.
- 명령: `/brainstorm <아이디어, 또는 직접 쓴 문서의 경로>` → `/kickoff`
- 팀, `/brainstorm`: 자유 브레인스토밍(lead가 제안하고 반박한다; 어젠다 없음) 또는 가져온 문서의 정리 → "기획서 만들어줘" → docs/BRIEF.md 작성(채택 / 나중 / 기각과 이유, 스케치는 부록) → 브레인스토밍이 비워 둔 슬롯만 한 번 묻기 → critic 사전 부검을 교정 라운드로 당신에게 → 승인 → 문서 커밋 → 상태판이 `/kickoff`를 가리킨다. 긴 브레인스토밍은 열 턴쯤마다 planner가 화이트보드로 남기므로, 끊긴 세션은 `/brainstorm`으로 이어진다.
- 팀, `/kickoff`: 기획서에서 헌장 도출(질문 없음) → 스택 ADR(critic 리뷰) → 확인 질문 한 번(스택, 헌장 세 줄, 기획서의 미결 항목) → 골격 → AGENTS.md(Risk paths 씨앗 포함)·ADR 확정·기획서의 채택 목록에서 백로그·walking skeleton 계획(핵심 흐름의 가장 얇은 조각)을 한 번에 → 전체 검증 → 문서 커밋 → lead가 `/hire`를 제안한다(모델 배정, 커밋; 이 세션에서 실행). 세션은 상태판을 쓴 채 끝난다. 첫 `/run`은 새 세션에서 한다(모델 배정은 세션 시작 때 로드된다) — 바로 시작하면 되고 `/handoff`는 필요 없다.
- 당신: 채팅에서 하듯 이야기하고 "기획서 만들어줘"라고 한다. 빈 슬롯에는 솔직히 답한다. **비목표 3개**, **측정 가능한 성공 지표**, **접는 기준**은 브레인스토밍이 빠뜨리는 것들이고 이후 모든 판정의 기준이다. 사전 부검 결과를 읽는다(항목마다 기본값이 붙어 있다). 기획서를 승인하고, `/kickoff`에서는 스택 ADR의 "왜 다른 대안이 아닌가"를 읽고 승인한다. 나중에 방향이 바뀌면 `/brainstorm`을 다시 실행한다. 기획서가 개정되고 헌장이 따라온다.
- 승인 기준: 성공 지표가 측정 가능한 문장인가. 기획서에 무엇을 왜 기각했는지 적혀 있는가. 골격에서 검증 명령이 실제로 통과했는가(verifier 보고).
- 흔한 실수: 브레인스토밍 안에서 기능 하나를 설계하기(그건 `/plan`의 사양서 라운드다 — lead가 말해 주고 부록에 한 줄만 남긴다). 문서를 가져와 놓고 빈 슬롯을 건너뛰기(보통 비목표와 접는 기준이 없다). 스택 결정을 팀에 통째로 맡기는 것 — 되돌리기 가장 비싼 결정이니 직접 고른다.

### 2.2 레거시 인수 / 리빌드 기획
- 언제: 기존 코드가 있고 고치거나 갈아엎어야 할 때.
- 명령: `/brainstorm <왜 리빌드하나, 목표 상태, 바뀌면 안 되는 것, 기한>`(한 문단과 "정리해줘"면 충분하다; 직접 쓴 문서도 된다) → `/assess <경로>`
- 팀, `/brainstorm`: 짧은 리빌드 기획서(Kind: 레거시) → 빈 슬롯 → 사전 부검 → 승인 → 커밋. 팀, `/assess`: 인벤토리(docs/ASSESSMENT.md; 기획서의 목표 상태와 충돌하는 "버그로 보이는 동작"은 표시된다) → 미지수 보고, 보존/수정 방침을 한 번에 → 전략과 첫 seam(ADR, docs/REBUILD_PLAN.md, AGENTS.md)과 기획서·평가에서 도출한 헌장(목표·비목표·성공 지표는 전략과 함께 당신이 확인한다) → 첫 seam의 parity harness 계획 → 문서 커밋 → lead가 `/hire`를 제안한다(리빌드는 critic·reviewer 비중을 높인다; 커밋; 이 세션에서 실행). 세션은 상태판을 쓴 채 끝난다. 하네스는 새 세션에서 계획 0001로 `/run`을 통해 만든다(모델 배정은 세션 시작 때 로드된다) — 바로 시작하면 되고 `/handoff`는 필요 없다. 이후 리빌드 단계마다 그 단계의 seam까지 먼저 확장한다. 인벤토리를 보고 목표가 달라졌으면 `/brainstorm`으로 기획서를 고친다.
- 당신: 왜 리빌드하는지와 바뀌면 안 되는 것을 말하고, 그다음은 세 가지 결정만 하면 된다. (1) "버그로 보이는 현재 동작"을 보존할지 수정할지 — 기본값이 채워진 질문 한 번: 기본값을 수락하거나 수정할 항목을 지목한다. (2) 전략(strangler fig / 모듈별 교체 / 전면 재작성). 기본값은 strangler fig이고, 전면 재작성은 팀이 근거를 대야 한다. (3) 팀이 도출한 헌장 줄 — 틀리면 고친다.
- 승인 기준: 리빌드하려는 seam에 대해 parity harness가 레거시로 PASS인가(docs/PARITY.md에 범위가 적혀 있다). 이게 없으면 그 단계 승인을 거부한다.
- 흔한 실수: 하네스 없이 "일단 새로 짜자". 문서화된 사양서(docs/specs/)가 없는 레거시에서 사양은 현재 동작뿐이다 — 그 너머에서 달라져야 할 것은 기획서만이 말한다.

### 2.3 설계·아키텍처 결정
- 언제: 되돌리기 어려운 결정(데이터 모델, 공개 인터페이스, 의존성, 스택).
- 명령: 별도 없음. `/plan` 도중 planner가 대안 비교표와 ADR 초안을 내고, critic이 pre-mortem을 붙인다. 에스컬레이션 기준에 걸리면 lead가 묻는다. 사양서가 있으면 그것이 입력이다: 사양서는 "무엇"을, ADR은 "어떻게"를 답한다.
- 당신: 비교표에서 **팀의 추천을 따르되, "결과(consequences)" 항목을 읽고 감당 가능한지** 본다. 되돌리기 어려운 결정만 직접 내리고 나머지는 위임한다(docs/DECISIONS.md에 남는다).
- 승인 기준: ADR에 대안이 2개 이상 있고 각각 기각 사유가 있는가.
- 흔한 실수: 모든 결정에 개입하기. 결정 로그를 안 읽어서 팀이 무엇을 자율로 정했는지 모르기 — 주 1회 DECISIONS.md를 훑는다.

### 2.4 백로그·우선순위
- 언제: 아이디어가 생겼을 때, 다음에 뭘 할지 모를 때.
- 명령: `/backlog <아이디어>` 또는 `/backlog`(정리만)
- 팀: docs/BACKLOG.md 갱신(기획서의 "나중"과 부록도 훑는다), 헌장 기준 우선순위, 제외 항목 분리, 상위 3개 제안.
- 당신: 상위 3개의 **순서**만 정한다. 항목 하나가 하루를 넘길 것 같으면 "쪼개라" 또는 "사양서로"라고 말한다.
- 흔한 실수: 백로그를 팀에 안 맡기고 머릿속에 두기. 그러면 헌장과의 충돌을 아무도 못 잡는다.

### 2.5 단일 개발 (기본 모드)
- 언제: 대부분의 작업. 한 세션에서 계획 하나.
- 명령: `/plan <백로그 항목 또는 기능>` → 접수(질문 1회) → 승인(승인 시 계획이 main에 커밋된다) → `/run <계획 파일>`. 단계를 따로 밟고 싶으면 `/build` → `/review` → `/ship`. 복잡한 기능이면 접수에서 "사양서 예"를 고른다: 채팅 2~3라운드 → docs/specs/NNNN-<slug>.md → 사양서 승인 → 계획.
- 팀: 접수(한 번에 네 문항: 사양서 여부 / 완료 조건 / 이번엔 제외 / 미리 정해진 것 — 요청에 이미 적혀 있거나 버그 줄·재계획이면 생략; 백로그 항목은 L 크기이거나 새 페이지·화면·API·데이터 모델을 언급할 때만 사양서 질문 하나) → 사양서를 골랐으면 라운드(구조 → 세부 → 당신의 교정 → 승인; 라운드마다 planner가 docs/specs/NNNN-<slug>.md에 적는다) → 계획(1~2절은 당신의 답 또는 사양서 그대로) → critic 리뷰(3단계 이상 또는 risk:high) → (에스컬레이션 질문) → 승인 커밋 → `/run`(같은 세션): 브랜치 → 단계별 구현·검증·커밋 → 리뷰·수정 → 출하·머지 판정. 멈추는 곳은 에스컬레이션, 수정 루프 3회 초과, 머지 승인뿐이다.
- 당신: 접수 선택지가 맞지 않으면 당신 말로 답한다(planner가 받아 적는다). 사양서 라운드는 당신이 길게 말하는 유일한 자리다: 당신 말로 답하고, 문서를 붙여 넣는 대신 경로와 링크(디자인 파일, 비슷한 화면, 외부 문서)를 주고, 교정 전에 초안 파일을 직접 읽는다. 그다음 **계획을 실제로 읽는다.** 완료 조건이 검증 가능한 문장인지, 논리 단계가 단계 크기 목표(기본 300줄) 안인지(넘으면 사유가 적혀 있는지), 비목표를 넘지 않는지. 승인 후에는 손을 뗀다. 질문이 오면 "결정 / 선택지 / 추천 / 기본값" 형식이니 추천을 따르거나 이유를 대고 바꾼다.
- 방향 수정: 승인된 사양서나 진행 중 계획은 `/plan <그 파일> 수정: <바뀐 것>`으로 고친다. 계획이 돌고 있으면 먼저 멈추라고 말한다(팀은 진행 중 단계의 검증까지 마치고 멈춘다). 기획서 개정과 같은 다섯 걸음이다. 이야기하고(lead가 대안과 영향을 말한다), "정리해줘"라고 하고, planner가 차이만 쓰고(계획은 마지막 PASS 뒤 단계만, 그 브랜치에서), critic이 바뀐 부분만 보고, 당신이 승인한다. 그다음 `/run <계획 파일>`이 같은 브랜치에서 이어지고, 사양서 개정은 다음에 고칠 계획을 알려준다.
- 승인 기준(계획): 완료 조건 · 단계별 검증 명령 · 롤백 방법 세 가지가 있는가.
- 흔한 실수: 계획 없이 큰 작업을 채팅으로 시키기. 한 세션에 두 계획 넣기. 팀이 일하는 동안 채팅으로 방향 바꾸기(멈추라고 말하고 `/plan <계획 파일> 수정: <바뀐 것>`). 정작 신경 쓰는 항목의 접수 답을 "알아서"로 넘기기 — 승인 단계에서 그것 때문에 계획을 반려하게 된다. 복잡한 기능을 사양서 없이 한 줄로 시키기. 습관적으로 `/plan`과 `/run`을 세션을 나눠 하기 — 긴 사양서 라운드 뒤에만 나눈다.
- 큰 diff가 정상인 경우: 스캐폴딩, 생성 코드, 락파일, 대량 포맷·이름변경, 삭제. 별도 커밋이고 종류가 표시돼 있으면 300줄 규칙은 적용하지 않는다. 대신 리뷰 기준이 다르다 — 재현 가능한가(생성기 재실행 diff 0), 논리가 섞이지 않았나, 빌드·테스트가 도는가. 당신은 그런 커밋을 줄 단위로 읽지 말고 그 세 가지만 본다.

### 2.6 병렬 개발
- 언제: 파일 단위로 서로 독립적인 기능이 둘 이상 있고, 순차로는 시간이 아까울 때. **처음 2주는 쓰지 않는다.**
- 명령: 메인 세션에서 `/spawn <계획 파일들>` → 팀이 계획마다 `../<레포>-<slug>` worktree와 `plan/<slug>` 브랜치를 만들고 새 터미널에서 실행할 명령을 알려준다 → 당신이 터미널을 열어 `cd ../<레포>-<slug> && opencode` → 그 세션에서 바로 `/build <계획>`(worktree 세션은 plan/<slug>에 머물고 상태판이 없다) → worktree 세션을 닫고, 끝난 브랜치는 메인 세션에서 `/integrate`로 main에서 딴 통합 브랜치(`integrate/<날짜>`)에 하나씩 머지 → `/ship`이 그 브랜치를 PR 하나(원격이 없으면 로컬 머지 하나)로 출하.
- 전제: `.opencode/`와 `opencode.json`이 커밋되어 있어야 worktree 세션에도 팀이 있다(아니면 `--global` 설치). `.env` 같은 미추적 파일은 worktree에 직접 복사한다. 계획은 승인 시 커밋되고, worktree가 보는 것도 그 커밋이다.
- opencode의 subagent는 worktree 격리 기능이 없어 "세션 내 병렬"은 지원하지 않는다. 병렬 = 세션 병렬이다.
- 당신: 각 계획의 "변경 파일" 집합이 겹치지 않는지 확인하고, 통합 순서(의존이 있으면 먼저)를 정한다. 진행 중엔 각 세션의 질문에만 답한다.
- 승인 기준: 겹치는 파일이 0개. 겹치면 순차로 돌린다.
- 한 사양서에서 나눈 계획들은 분할 제안에서 파일이 겹치지 않고 의존이 없다고 나온 경우에만 병렬로 돌린다. 사양서의 완료 조건은 마지막 계획이 출하된 뒤 전체로 확인한다.
- 흔한 실수: 한 기능의 단계들을 병렬로 나누기(단계는 순차다). 통합을 여러 브랜치 동시에 하기(항상 하나씩).

### 2.7 리뷰
- 언제: `/build`가 끝났을 때(병렬 브랜치는 `/integrate`가 스스로 리뷰한다).
- 명령: `/review [기준 브랜치]`
- 팀: 위험도에 비례해 렌즈를 정한다 — 기본 correctness + security 2개, risk:high·논리 diff 600줄 초과·핫패스면 performance + maintainability까지 4개(risk:high는 기계적이다: 규칙 파일의 "Risk paths"에 걸린 파일이나 에스컬레이션 항목. 팀은 올릴 수만 있고 걸린 것을 내리지 못한다). 병렬 투입 → blocker·major 취합 → 수정 루프(최대 3회; 재리뷰는 수정 diff만, 지적한 렌즈만) → 전원 APPROVE.
- 당신: 서로 충돌하는 지적이 올라오면 판정한다. 그 외엔 결과 요약만 읽는다. 리뷰어 지적 중 반복되는 것이 보이면 `/retro` 후보로 메모한다.
- 흔한 실수: 리뷰 결과를 안 읽고 승인. 리뷰어 지적을 당신이 직접 고치기(implementer에게 시킨다).

### 2.8 QA / 검증
- 언제: 항상 자동으로 돈다(기본은 단계마다 verifier; 운영 프로필로 `/build` 끝의 전체 검증으로 옮길 수 있고, 그때는 그것이 독립 판정이다). 사람 QA는 출하 전.
- 명령: 별도 없음. 필요하면 `@team-verifier 전체 검증` 으로 직접 호출.
- 팀: AGENTS.md의 "빠른 검증"과 "전체 검증"을 실행하고 PASS/FAIL과 실패 개수만 보고.
- 당신: **초록불을 믿지 말고 증거를 본다** — 어떤 명령을 실행했고 테스트가 몇 개 돌았는지. 테스트가 0개면 PASS는 의미가 없다. 출하 전에는 제품을 직접 한 번 써본다(사용자 관점은 자동화가 못 잡는다).
- 테스트가 없는 레포라면: 첫 작업은 기능이 아니라 검증 수단이다. `/plan "빠른 검증 명령 만들기"` 부터. 이게 없으면 팀 전체가 "그럴듯한 코드" 생산기가 된다.
- 흔한 실수: AGENTS.md의 검증 명령이 실제와 다른 채로 방치. 팀이 테스트를 skip해 통과시킨 것을 못 잡기(reviewer correctness 렌즈가 보지만, PR의 테스트 diff는 직접 훑는다).

### 2.9 디버깅 (원인 불명 버그)
- 언제: 증상은 있는데 원인을 모를 때.
- 명령: `/plan "버그: <증상>. 재현 테스트를 먼저 만들고, 원인을 확정한 뒤 수정"` (접수 질문 없음: 재현 조건이 곧 사양이다)
- 팀: Explore 조사 → 가설 → **실패하는 재현 테스트** → 수정 → 테스트 통과 → 리뷰.
- 당신: 재현 조건을 최대한 구체적으로 준다(입력, 환경, 로그, 언제부터). "가끔 이상함"은 계획이 못 된다. 팀이 재현 테스트 없이 수정으로 직행하면 되돌린다.
- 승인 기준: 수정 전에 실패하고 수정 후에 통과하는 테스트가 diff에 있는가.
- 흔한 실수: 증상 완화 패치를 승인하기. 원인이 데이터/인터페이스에 있으면 에스컬레이션 질문이 오니 그때 결정한다.

### 2.10 트러블슈팅 (팀이 헛돌 때)
- 신호: 같은 실패 3회, 질문이 반복됨, diff가 계획과 무관하게 커짐, 컴팩션이 2회 이상.
- 당신이 하는 것, 순서대로:
  1. 멈춘다. 고치려고 대화로 끌고 가지 않는다.
  2. `/handoff` 로 상태를 남기고 세션을 버린다. 새 세션에서 `/resume`.
  3. 그래도 같은 지점에서 막히면 계획이 틀린 것이다. `/plan` 을 다시 세운다(단계를 더 잘게).
  4. 환경 문제(의존성, 권한, 명령 불일치)면 verifier 보고에 "환경 문제"로 나온다 — 이건 당신이 직접 고친다.
  5. 두 번째 반복이면 `/retro`. 느림·비용이 문제면 `/hire` 로 배정을 바꾼다.
- 흔한 실수: 헛도는 세션에 "다시 해봐"를 반복. 컨텍스트가 오염된 세션은 살릴수록 나빠진다.

### 2.11 병합
- 로컬 통합(`/integrate`): 병렬 브랜치를 main에서 딴 통합 브랜치(`integrate/<날짜>`)에 하나씩 리뷰 → 머지 → 충돌은 implementer가 해소하고 재리뷰 → verifier. 그다음 `/ship`이 그 브랜치를 계획 브랜치처럼 출하한다(PR 하나 또는 로컬 머지 하나, METRICS는 계획마다 한 줄). 머지가 실패하면 팀이 스스로 되돌리고 보고한다. 당신은 그다음을 정한다.
- main 머지: `/ship`이 저장소 상태를 보고 정책을 **자동 판정**한다. 당신이 설정을 고칠 일은 없다.
  - 원격 없음 → `local`: PR 설명이 docs/prs/NNNN-<slug>.md 로 남고, lead가 승인을 묻는다. 볼 것은 PR과 같다(검증 증거, 리뷰 처리, 롤백). 승인하면 로컬 main에 `merge --no-ff`.
  - 원격 있음, 보호 없음 → `manual`: 팀이 push + PR(`risk:low|high`)까지. 당신이 PR을 보고 머지한다. `risk:high`면 diff를 직접 읽는다.
  - 원격 있음 + main 보호(필수 체크 = CI) + auto-merge 허용 → `auto-low-risk`: `risk:low`는 CI 통과 시 자동 머지, `risk:high`만 당신이. 즉 "자동 머지를 켜는 행위" = GitHub에서 보호와 auto-merge를 켜는 것이다.
  - `/policy`로 현재 판정과 근거를 볼 수 있다. 판정을 강제하고 싶을 때만 `/policy manual` 또는 `/policy auto-low-risk`(AGENTS.md에 override 기록). `/policy auto`로 자동 판정 복귀.
- 팀은 어느 판정에서도 force push와 main 직접 push를 못 한다(훅). 머지는 항상 PR 또는 승인된 로컬 머지를 통과한다.
- **GitHub를 붙이는 날**: `git remote add origin …` 과 첫 push. 그다음 `/ship`부터 자동으로 PR 흐름이다. main 보호 + auto-merge를 켜는 순간 자동으로 auto-low-risk가 된다.
- 흔한 실수: 브랜치 보호 없이 auto-low-risk 켜기. 충돌 해소 diff를 리뷰 없이 넘기기(설정상 correctness 재리뷰가 붙지만 확인).

### 2.12 출하·릴리즈
- `/ship`: 전체 검증 → 문서·CHANGELOG → PR 설명 → push → PR. 당신은 PR 설명의 "검증 증거"와 "리스크와 롤백"을 읽는다. 둘 중 하나가 비어 있으면 머지하지 않는다. 사용자 대면 PR에는 "직접 확인" 절이 있다. 명령을 실행하고 단계를 밟아 본 뒤 머지한다(이런 PR은 자동 머지되지 않는다). PR이 열리면 세션은 main으로 돌아와 있다. 다음 `/plan` 전에 머지한다(다음 세션이 머지를 당겨 온다).
- `/release [버전]`: 버전 제안 → 전체 검증 → CHANGELOG 확정 → docs/releases/<ver>.md → 태그 명령 제시. 당신이 태그를 push한다. 인터페이스 변경이 있으면 major/minor를 묻는 질문이 온다.
- 흔한 실수: 릴리즈 노트를 팀 관점(무엇을 바꿨나)으로 두기 — 사용자 관점(무엇이 달라지나, 알려진 문제, 롤백)이어야 한다.

### 2.13 세션 종료
- 언제: 단계 도중에 멈추는 세션, 컴팩션이 2회 이상 됐을 때, 헛돌 때, 작업이 진행 중인 채 하루가 끝날 때 — 끝난 `/ship`이나 `/plan` 뒤에는 아니다(상태판과 커밋이 이미 남아 있다).
- 명령: `/handoff [메모]`
- 팀: 열린 브레인스토밍·사양서 라운드·수정 논의가 있으면 planner에 체크포인트 → docs/STATUS.md 작성(로컬, 커밋하지 않음; 진행 중인 사양서와 라운드 포함) → 미커밋 코드는 `wip:` 커밋, 미커밋 문서는 `docs:` 커밋 → "끝낸 것 / 결정 대기 / 다음 세션 첫 행동" 보고.
- 당신: 보고의 **다음 행동 첫 항목**이 당신 생각과 맞는지 본다. 틀리면 그 자리에서 고쳐 말한다(팀이 STATUS를 수정). 결정 대기 항목은 지금 답하거나 다음 세션 첫머리에 답한다.
- 흔한 실수: 단계 도중에 `/handoff` 없이 창 닫기 — 커밋 안 된 변경과 판단 근거가 사라진다.
- 옛 흐름에서 docs/STATUS.md를 커밋했던 프로젝트를 올릴 때: 설치 스크립트를 다시 실행한다(.gitignore 줄이 추가된다). 다음 이정표 커밋이 그 파일을 저장소에서 뺀다.

### 2.14 신규 세션 재개
- 명령: 새 세션 → 주입된 파일에 상태판이 있으면 `/resume [메모]`. 헌장만 있으면 `/plan`으로 바로 시작한다(진행 중인 것이 없다). 짧게 끊긴 경우만 `opencode -c` 로 직전 세션을 이어간다. 길게 이어진 세션은 요약 위에 요약이 쌓여 품질이 떨어지니 기본은 새 세션이다.
- 팀: 상태판(자동 주입) · 계획 · git 상태를 대조 → 어긋나면 저장소를 믿고 상태판 수정 → 로컬 main을 origin과 동기화(fast-forward, squash 머지 뒤에는 로컬 이정표 커밋을 rebase) → PR이 머지된 상태판은 끝난 것으로 처리(브랜치 삭제, 다음: `/plan`) → 마지막이 FAIL이면 verifier 먼저 → 결정 대기 질문 → 다음 행동부터(중단된 사양서면 `/plan docs/specs/NNNN-<slug>.md`).
- 당신: 대기 중인 결정에 답한다. 상태판과 저장소가 어긋났다는 보고가 오면 저장소가 맞다.
- 규칙: 한 세션 = 한 계획. 다른 계획은 새 세션.


### 2.15 회고
- 언제: 같은 실수가 두 번, CEO 개입이 잦아질 때, 장애 후, 릴리즈 후.
- 명령: `/retro <계획 slug | 세션 | 사건>`
- 팀: docs/METRICS.md 추세(재작업·질문·소요)를 먼저 보고 → 재작업·검증 실패·리뷰 blocker·CEO 개입이 난 지점을 3개 이내로 특정, 근본 원인 → 원인마다 재발 방지책과 그것이 박힐 자리(규칙 한 줄 / 스킬 / 훅(하드 차단) / 계획 형식) 제안 → 승인된 것만 planner가 반영. 접수·사양서 라운드는 개입으로 세지 않는다. 교정 상한에 걸린 사양서나 기획서, 두 번 이상 수정된 계획은 회고 대상이다.
- 자리를 고르는 기준: 매번 지켜야 하는 사실·금지 → AGENTS.md 한 줄 / 여러 단계의 절차 → 스킬 / 프롬프트로 못 믿고 물리적으로 막아야 하는 것 → 훅 / 계획 단계에서 놓친 것 → 계획 형식.
- 당신: **위반 사례가 있는 규칙만** 승인한다. 일반론("항상 신중하게")은 거절한다. AGENTS.md이 300줄을 넘기 시작하면 절차를 스킬로 빼라고 한다.
- 흔한 실수: 회고 없이 같은 프롬프트를 반복하기. 규칙을 잔뜩 승인해 AGENTS.md을 비대하게 만들기.

### 2.16 채용 (모델 배정)
- 언제: `/kickoff`·`/assess` 직후(lead가 제안한다), 예산 티어가 바뀔 때, 팀이 너무 느리거나 비싸다고 느낄 때.
- 명령: `/hire [메모]`
- 팀: `opencode models`로 목록을 얻고, 예산 티어·프로젝트 성격·병렬 계획·강조할 역할을 한 번에 묻는다 → 역할 × 모델 표를 이유와 함께 제안 → 운영 프로필(기본 리뷰 렌즈 2/4, 병렬 허용, critic 최소 단계, 단계별 verifier, 단계 크기 목표)도 제안 → 승인 후 스크립트 하나가 model 줄만 바꾸고 다른 하나가 AGENTS.md에 "운영 프로필" 절을 쓴다.
- 당신: 질문에 답한다. 특히 사내 모델처럼 lead가 모르는 모델은 **어느 것이 가장 강하고 어느 것이 가장 빠른지** 당신이 알려줘야 한다(lead는 추측하지 않는다). 표는 승인하거나 한두 줄만 바꾼다.
- 승인 기준: planner·critic·reviewer 에 가장 강한 모델이 갔는가. verifier 는 가장 빠른 모델인가. low 티어면 병렬·4렌즈가 기본에서 빠졌는가.
- 흔한 실수: 비용 때문에 reviewer 를 먼저 깎기(품질이 가장 먼저 무너지는 자리다 — 깎을 거면 implementer 부터). 새 세션을 열지 않고 반영을 기대하기(모델 배정은 새 세션부터).

### 2.17 핫픽스 (작고 명확한 수정)
- 언제: 한 문장으로 말할 수 있고 확인 방법이 자명한 변경 — 재현이 있는 결함, 잘못된 문구·설정값·기본값, 의존성이나 버전 올리기. 새 동작, 설계 판단이 필요한 것, 규칙 파일의 "Risk paths" 아래 파일은 해당 없음: 그건 `/plan`이다.
- 명령: `/hotfix <무엇을 왜 고치는지>` — 한 번에, 계획 파일도 접수도 없다.
- 팀: 브랜치 `hotfix/<slug>` → implementer(수정, 논리 수정이면 회귀 테스트, 빠른 검증, 당신의 요청을 본문에 인용한 커밋 하나) → 상한 검사(파일 3개·논리 50줄 초과 또는 Risk path면 멈추고 묻는다 — risk:high로 진행 또는 계획으로 전환) → 전체 검증 → correctness 1렌즈 → 증거를 담은 PR(auto-low-risk여도 자동 머지 없음) 또는 승인 후 로컬 머지 → docs/METRICS.md에 `hotfix:` 표시 한 줄.
- 당신: 고칠 방법이 아니라 결함이나 잘못된 값을 말한다(방법을 알면 적어도 된다). 그다음 diff를 읽는다 — 전부 읽을 만큼 작고, 사람이 보는 유일한 지점이 이 PR이다 — 그리고 머지한다.
- 승인 기준(PR): 검증 증거에 실행한 명령이 있는가. 논리가 바뀌었으면 회귀 테스트가 diff에 있는가. diff가 요청 범위 안에 머무는가.
- 흔한 실수: 설계 판단이 필요한 변경을 핫픽스로 시키기, 같은 영역에 핫픽스 세 번 연달아(그건 `/plan`이고 `/retro` 대상이다 — METRICS에 `hotfix:` 줄이 쌓인다). diff를 읽지 않고 초록불만 보고 머지하기.

## 3. 리듬

- 하루(1~2시간): `/resume` → (백로그에서 하나) 접수 질문(또는 사양서 라운드)에 답하고 `/plan` 승인 → `/run` 동안 손 떼기(게이트 질문에만 답) → 머지 판정대로 → (`/handoff`는 도중에 남은 것이 있을 때만).
- 주: `/backlog` 로 다음 주 상위 3개, `/release`, docs/DECISIONS.md 훑기, 필요하면 `/retro`.
- 첫 주: 1일차 `/brainstorm` 뒤 `/kickoff`(또는 `/assess`) + "1분 안에 도는 검증 명령" 확보 → 2~3일차 walking skeleton → 4~5일차 기능 2개를 plan→run → `/retro` 한 번. 2주차부터 병렬.
- 지표 셋: 재작업 횟수 / 세션당 질문 수(접수 질문과 사양서 라운드는 정상이며 세지 않는다) / 계획 승인→머지 시간. `/ship`이 상태판의 Counts 줄(일이 일어날 때마다 세고, 출하 때 재구성하지 않는다)에서 docs/METRICS.md에 계획마다 한 줄 남기고 `/retro`가 읽는다. 줄어들면 세팅이 맞는 것이다.

## 4. 승인 체크리스트

기획서를 승인하기 전:
- [ ] 성공 지표가 숫자이거나 관찰 가능한 사실이다
- [ ] 구체적인 비목표가 3개 이상 있고, 접는 기준이 있다
- [ ] "채택"은 역량 한 줄씩이지 흐름이나 화면이 아니다(그건 사양서)
- [ ] 기각된 아이디어마다 이유가 있다
- [ ] 미정 항목마다 언제 정할지 적혀 있다
- [ ] Kind가 신규 또는 레거시(경로)로 적혀 있어 다음 명령이 분명하다

사양서를 승인하기 전:
- [ ] "완료 조건"이 모두 검증 가능한 문장이다
- [ ] "이번엔 제외"가 비어 있지 않다
- [ ] 미정 항목마다 언제 정할지 적혀 있다
- [ ] "어떻게"(스택·스키마 설계·라이브러리)가 들어 있지 않다
- [ ] 두 쪽 이하이고, 붙여 넣기 대신 링크다
- [ ] 누가 언제 쓰는지 적혀 있다

계획을 승인하기 전:
- [ ] 완료 조건이 검증 가능한 문장이다 (명령·테스트·수치)
- [ ] 단계마다 검증 명령이 있고, 논리 변경 단계는 단계 크기 목표(기본 300줄) 안이거나 넘는 사유가 적혀 있다(2배는 넘지 않는다). 기계적 변경(스캐폴딩·생성·락파일·포맷·삭제)은 별도 단계로 분리돼 있다
- [ ] 비목표·헌장과 충돌하지 않는다
- [ ] 롤백 방법이 적혀 있다
- [ ] 1~2절이 당신의 접수 답 또는 사양서와 일치한다
- [ ] critic이 APPROVE 했다(실행됐다면)

승인 후에는 `/run` 하나로 끝까지 간다. 당신이 다시 불리는 건 에스컬레이션·수정 루프 초과·머지 승인 세 경우뿐이다.

PR을 머지하기 전:
- [ ] 검증 증거에 실행 명령과 실패 0건이 적혀 있다 (테스트 개수 0이면 거부)
- [ ] 리뷰 지적과 처리 내역이 있다
- [ ] `risk:high`면 스키마·인터페이스·보안 diff를 직접 읽었다
- [ ] 테스트 파일 diff에 skip·삭제·약화가 없다
- [ ] 기계적 커밋(scaffold/gen/mechanical/deps)에 논리 변경이 섞여 있지 않고, gen은 재생성 diff 0이다
- [ ] 롤백 방법이 있다
- [ ] 사용자 대면 PR이면 "직접 확인" 단계를 직접 밟아 봤다

## 5. 토큰이 새는 곳과 막는 법
- subagent 상태를 반복 확인: lead 규칙으로 금지했다(동기 호출, 완료까지 대기). 그래도 보이면 `/retro` 대상이다.
- 진행 서술("이제 …하겠습니다"): 규칙으로 금지. 결과와 결정만 말하게 한다.
- 자동 주입 문서가 비대해짐: CHARTER 60줄·STATUS 30줄 상한. STATUS는 lead가 상한 안에 유지하고, CHARTER는 넘치면 planner가 분리한다. opencode 에는 (Claude Code 의 session-start 훅과 달리) 강제 상한이 없어서, 이 선을 넘긴 파일은 그대로 매 세션 전체가 주입된다.
- 작은 계획에 critic·4렌즈: 논리 단계 3개 미만·risk:low 면 critic 생략; 논리 diff 600줄 미만·risk:low 면 리뷰는 2렌즈. 위험도는 규칙 파일의 "Risk paths"와의 파일 대조이지 판단이 아니다. 팀은 올릴 수만 있고 걸린 것을 내리지 못한다. 운영 프로필(/hire)로 조정.
- 접수는 계획당 최대 한 번 묻는다. 버그 줄·재계획·백로그 항목(L 크기나 새 페이지·화면·API·데이터 모델의 사양서 질문 하나는 예외)에도 질문이 오면 `/retro` 대상이다.
- 사양서 라운드는 짧은 대화 원칙의 예외다: 경로와 링크를 주고 문서는 붙여 넣지 않는다(planner가 읽는다). 기억은 파일이니 긴 사양서 라운드 뒤엔 "승인, 계획은 다음 세션에"를 고르고(사양서는 커밋된다) `/plan docs/specs/NNNN-<slug>.md` 로 재진입한다.
- 브레인스토밍은 lead 컨텍스트에 쌓인다: 열 턴쯤마다 planner가 체크포인트를 남기고, 길었으면 `/kickoff`나 `/assess`는 새 세션에서 한다(상태판이 가리킨다).
- 당신 쪽: 같은 질문을 세션마다 다시 하지 않기 — 결정은 docs/DECISIONS.md 에 남기고 lead 가 따르게 한다. 한 세션에 계획 하나. 컨텍스트가 무거워지면 `/handoff` 후 새 세션.

- 계획 없이 큰 작업을 채팅으로 시키기, 복잡한 기능을 사양서 없이 한 줄로 시키기

- 팀이 일하는 도중 채팅으로 방향 바꾸기 (멈추라고 말하고 `/plan <계획 파일> 수정:`)
- 리뷰어 지적을 직접 고치기
- 헛도는 세션을 살리려 하기
- 브랜치 보호 없이 자동 머지 켜기
- 회고에서 일반론 규칙을 승인하기
- AGENTS.md의 검증 명령을 실제와 다르게 두기
